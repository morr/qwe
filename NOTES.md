## Уроки живых замеров

**`QWE_PERF_NOAPPNAP=1` обязателен в строке запуска** (№19: без него процесс
деградировал в App Nap посреди серии — все потоки T в ps -M, загрузки в 2.4–2.7×
медленнее с третьей-четвёртой; диагностика — резкий скачок ВСЕХ шагов загрузки между
соседними загрузками; четыре замера выброшены); **`pwd &&` — в самой команде запуска
приложения** (№19: cd ворктриа в фоновом build-задании не персистентен — «сторона A»
снята с чужого бинарника; числа переклеены, но урок дорогой); `$b ready <log>` после
первой загрузки всегда «готов» — для серий переключений ждать НОВУЮ строку warmup
(grep-счёт до/после), иначе `res set City` гейтится в Loading и переключение теряется
молча; **.settings перезаписывается на выходе приложения — город последней загрузки
становится стартовым, первая строка «navmesh filled in» серии бывает Парижем, а не
Тула-выбросом** (№19); после тёплой сборки ready может вернуть «готов» мгновенно, а
первая загрузка — уехать до вызова: окно по таймстемпам считай только между
строками, которые точно после старта запуска; никаких параллельных компиляций при
живых замерах (check.sh рядом замедлял загрузки 10×); `algorithm=Hpa` в сохранённых
настройках запускает сборку northstar (22–28 с) после каждого входа в Live — для серий
переключений ставить `res set PathfindingAlgorithm . '"Astar"'` сразу после первого
ready (для одиночных стартовых загрузок не нужно); после warmup/pause `res get
SimSpeed` читается в переходном состоянии — бери steady-state из строки `brp run`
(actual Nx) и счётчик `frame spike`; pgrep по полному пути ворктриа не находит процесс
(argv[0] относительный), pid брать у `$b alive`; check.sh не принимает Cargo.toml и
.md (rustfmt падает E0758); окно snapshot→warmup шумнее отдельного шага: −111 мс шага
дали −0.07 с окна, −29 мс шага не видны вовсе — меряй целевой шаг по его строке
лога, окно — как вторичный признак; вид владельца (Париж, zoom 0.4, Astar)
настраивается одним прогоном базы: системный settings.toml перезаписывается на
выходе, worktree при первом запуске сеется из него
(`prefs.rs::seed_worktree_settings`) — у сторон A/B файлы идентичны без ручной
возни (№21);
**отчёт слоя печатает Duration Debug-ом: под секундой — `966.271583ms`, над —
`1.072s`**, грепай `in [0-9.]+m?s`, а не `in [0-9.]+s` (№21: первая серия стороны
B выглядела одной строкой из шести);
**RSS-сэмплирование — пауза сразу после warmup и фикс-стабилизация 5–6 c**:
первые секунды после Live догружают меши в GPU (+1.3–1.6G за секунды), без
паузы и стабилизации кривая шумит на ±1.4G (№23: «низкие» первые загрузки
оказались недосэмплированными, не эффектом зонда); реальная цена города —
dirty-footprint `vmmap --summary`, разрыв ps-RSS↔footprint — MADV_FREE'd
свободные страницы; `heap -addresses all` печатает строки `addr: тип (N
bytes)`, у Rust-аллокаций тип `non-object` — гистограммы только по размерам;
**статусы двух чекаутов — порознь**: склеенный вывод двух `git status` в одном
вызове читается как один (№23: Edit по пути главного чекаута прочитан как
worktree-правка, врезка в бинарь не попала — укус №5/№14 с изгибом);
**`res set City` тем же городом триггерит перезагрузку** (`retuned` = is_changed &&
!is_added) — серию загрузок одного города можно гнать без переключений на другой
город; **дрейф машины между сессиями больше разброса внутри сессии** — A/B сравнивай
только чередованием внутри одной сессии; временные таймерные врезки снимай ДО
коммита, и помни: повторные Edit с одним анкором дублируют блок (grep 'TEMP' перед
коммитом).

**счёт загрузок в пробе веди от строк лога после старта запуска** (№30): свой же
`res set City` — в том числе тем же городом — даёт загрузку, неотличимую в счёте
от «второй загрузки»; стартовый город после любого выхода приложения — город
последней загрузки, не тот, что в стандартном settings.toml, так что проба
«стартует Парижем, потом переключаю» может стартовать уже целевым городом и
сама съесть свой яд до всякого переключения; проверки файлов после `cd` в
worktree — только по абсолютным путям (греппы по относительному NOTES.md
читают копию ворктриа, №30).

**сэмплер CPU — pid фиксировать до серии, не резолвить в цикле** (№36):
`lsof -ti tcp:15703` каждые 0.5 с (сканирует все процессы) уронил живое
приложение в 3–7-секундные разрывы между кадрами на ВСЁ время серии; после
pkill сэмплера разрывы исчезли мгновенно. Порядок: `$b alive` → pid → цикл
только на `ps -o time=` + `ps -M` (как в первой серии звена — безопасно).

**бенч map_meshing между сессиями плавает сильнее живых окон** (№36):
fences 1752–2159 и road 1.52–1.96 против баз №35 (1083 / 1.09) при чистых
канарейках живого приложения того же кода; caffeinate бенчу не помогает —
сравнивать пары внутри сессии, между сессиями — только относительную
структуру слоёв.

**здоровье машины при живых замерах проверять ДО серии** (№31): `res get
SimSpeed` на Париже Astar несёт affordable 20+; обвал affordable (№31: 0.56 при
requested 1.0) — машина под внешней нагрузкой (в ps — ZCode GPU-процесс 43.7 %
+ opendirectoryd 36 %), рамочные замеры после такого момента — мусор (спайки
100–400 мс на паузе, кадр 4.1 с); доверять можно только учётке по таймстемпам
строк лога; ранние замеры той же сессии, сошедшиеся с известными базами
записей 61–63, остаются валидными. Деградация приходит волнами, привязанными
к активности собственной сессии (ZCode Helper 51 %; №33: из четырёх запусков
два деградировали ×25–100 разом при живом NOAPPNAP+caffeinate, два — чистые);
канарейки-шаги загрузки (снапшот-рид ~92 мс, fill ~137 мс) различают
мгновенно; **loadavg не показателен** — на 14-дневном аптайме читал 150–160
при 5 бегущих процессах и 85 % idle (№33); **деградация бывает внешней и
именованной: XProtectRemediatorPirrit (периодический скан macOS) жрал 72–93 %
CPU ~15 минут и вздул все шаги загрузки ×3–4** (№34, прогон выброшен
целиком) — перед серией и между прогонами проверять ps на не-своих
пожирателях и ждать их конца; бинарь напрямую не запускать
(«no LC_RPATH's found» — только через cargo run), якорь спавна — pgrep-поллер
с gdate (у BSD date нет %N).

**первый запуск свежего ворктриа — прогон целиком испорчен** (№35): холодный
кеш снапшота (рид 165 мс против 92) + сборка бинаря перед стартом + сидинг
настроек — выкидывать прогон, второй запуск ворктриа уже чистый; вид
владельца (Париж@0.4, Astar) ставится одним прогоном — старт Тулой →
`res set City . '"Paris"'` → ждать новую warmup-строку → quit
(`START_ZOOM` = 0.4, так что переключение города само даёт вид владельца).

**`res set` — всегда три аргумента: ресурс, путь, значение** (№42): дву-
аргументная запись `res set City '"Paris"'` скрипт молча отвергает
(«needs <Resource> <.path> <json-value>»), свит без ожидаемой warmup-строки
досиживает свой таймаут — потерянный прогон заметен только по числу
реальных переключений; скриптовые однострочники из старых секций Notes
с двуаргументной формой не копировать. Скриншот живьём — `shot` без
аргумента, файл переносить руками: приложение пишет в свой cwd
(`screenshot.png` + `.small.png`), кастомный путь скрипт ждёт зря
(30 с на попытку). Свит больше 4–5 городов — фоном сразу: цикл из
12 городов не влезает в foreground-таймаут 10 минут (№42).

**перед пробой перф-темы читать ЕЁ запись журнала, не только README-хвост** (№37,
дорогое переоткрытие): README до записи 67 — указатель, а вердикты по темам
лежат в самих записях; угол «предфильтр клипа находки лоскутов» был закрыт

Задача: сорок первое звено — обзорная форма (меню малых оптимизаций
исчерпано, №37–39). Угол — Cargo-профили сборки: ни один из углов №1–№40 их
не брал, перф-журнал по теме чист (все «профили» там — sample-профили CPU).
master на старте 9645ed6b.

## Методика

Worktree perf41 (сид owner-view: Париж@0.4, Astar), BRP 15703,
`QWE_PERF_NOAPPNAP=1 caffeinate -i`. Формула окна: строка
`transition: Playing => Loading` → `warmup: … routed` по таймстемпам лога;
канарейки — снапшот-рид (~92 мс) и fill. Замена профиля — только
`cargo clean -p qwe` + контроль «Compiling qwe» в логе (почему — урок ниже).

## Найдено

- **opt-level 1 → 2 у `[profile.dev]` (qwe-код): тёплое окно Парижа
  3.78–3.98 → 3.58–3.73 с (−0.2 с, −5 %, диапазоны восьми и шести загрузок
  не пересекаются)**. Весь эффект — снапшот-рид (bincode-десериализация
  снапшота мономорфизирована в qwe-коде): 90.7–93.4 → 56.7–59.4 мс (−35 %);
  fill −10..−20 % (шумно), `routed` без разницы. Чистая пересборка qwe:
  88 с (opt1) против 89 с (opt2) — цена итерации не растёт.
- **opt-level 3 отклонён без рантайм-замера**: чистая пересборка 537 с
  против 88 с (×6); его живая серия легла на волну машины (канарейки ×2–6)
  и выкинута целиком.
- **Грабли профилей** (в постоянный раздел «Уроки»): смена
  `[profile.dev] opt-level` сама по себе не инвалидирует cargo-кеш
  («Finished in 0.59s», бинарь старый); touch-пересборка (5–9 с) может
  поднять CGU из инкрементального кеша чужого профиля; сидинговая
  пересборка B-серии ушла не с тем профилем — её окна 7.0 с при канарейках
  ×1.3–1.9 выкинуты. Только `cargo clean -p qwe` даёт подтверждаемую смену.
- **Свип bevy-фич — все живы**: `pan_camera` — модуль крейта
  `bevy_camera_controller` (camera.rs/dev.rs/loading.rs), `bevy_dev_tools` —
  `log_transitions` (loading.rs), `bevy_camera_controller` — тот же
  PanCamera. Правок не нужно.
- `[profile.release]` отсутствует (дефолт: codegen-units 16, LTO off) —
  зона бенчей, не продукта; не резалась (хвост, не пункт меню).

## Негативы, остатки и уроки (следующим звеньям)

- **Влитие opt2 — решение владельца** (пункт в docs/deepening-plan.md,

  осознанный трейдофф скорости правок против скорости запуска. Если решит
  брать — одна строка `opt-level = 2`; инкрементальную цену правок кода при
  opt2 не измерял (clean-цена одинакова).
- Окна B-1 (7.0 с) и opt3-серии — выкинуты целиком по канарейкам; уроки
  №31/№33/№34/№36 о волнах подтвердились ещё раз (волна приходит рядом с
  активностью собственной сессии, между сторонами чередования).
- Правок кода нет → check.sh не требовался; ветка perf41 = master
  9645ed6b, ворктри чист — удалить

- Уроки №16–40 подтвердились; cwd-дисциплина без нарушений (cd отдельным

# NOTES — обзор №40 (угол: динамика долгого прогона — первый soak цепочки: Париж на requested 30 через волны CPU-голода; вердикт: мир устойчив — инвариант населения бит-в-бит ×6, 0 паников; находки: DemonStyle.cap=20 — сохранённый pref владельца (спавнер честен), шаг footprint 3.3→7.0G под голодом отложен в план с триггером, спайки волн — rest-сигнатура среды; правок кода не потребовалось, без коммитов)

Задача: сороковое звено — обзорная форма (меню оптимизаций исчерпано,
№37–39). master на старте 5914fdbe. Угол свежий: ни одно звено не гоняло
сим на длинной дистанции — №10 делал пять загрузок с короткими наблюдениями
после warmup, №9 свипал рост коллекций статически; динамика сущностей и
памяти на часах сим-времени не была проверена никем, включая конечное
состояние вымирания населения.

## Методика

Worktree perf40 (сид owner-view settings.toml: Париж@0.4, Astar), тёплая
сборка, `QWE_PERF_FRAME_SPIKES=30 QWE_PERF_NOAPPNAP=1 caffeinate -i`, BRP
15703. requested 30 с T0; 7 точек за ~25 мин стены, ~4700 сим-с (~1.3
сим-ч) мира. Сэмпл = пауза → counts/ресурсы/память → resume.

## Найдено

- **Договор населения держится на всей дистанции**:
  alive+killed+escaped==20000 бит-в-бит на всех шести сэмплах (T0
  19984+16+0 … T5 17003+2800+197); debug-census-ассерт не сработал ни разу
  за ~286k тиков. Население убывает монотонно (спавн людей только на входе
  в мир), escaped работает (197), трупы 1:1 с killed, BloodPool 1:1 с
  трупами, души транзиентны; сущности 28310 — рост следует за трупами
  (потолок HUMAN_COUNT).
- **Демоны стоят на капе 20 — и это не баг**: сохранённый pref владельца
  `DemonStyle.cap=20` (ползунок Sim-вкладки персистится); спавнер честно
  остановился на капе — таймер замораживается при spawned>=cap
  (demon/systems.rs::tick_spawner). Первая живая демонстрация договора
  «настройки переживают выход» в динамике мира.
- **Регулятор и guard пережили волны голода по дизайну**: под волнами CPU
  effective отступал до 0.135×, guard абсорбировал взрывы в TickDebt
  (deferred 3241 с кумулятивно), в тихих окнах долг стекал до owed 0 и
  скорость возвращалась к ~19×. 0 паников/ERROR за весь soak; WARN 2
  (известные load-time degenerate polygons).
- **Спайки волн — rest-сигнатура**: разборы tick spike называют rest
  100–500 мс (флеши/синк-поинты/пул) при тихих сегментах — голод машины,
  не работа какой-то системы (шторм 04:36:59–04:37:19 совпал с обработкой
  сэмпла T1; уроки №31/№33/№34 подтверждены soak-ом).
- **Шаг footprint 3.3→7.0G** в самом тяжёлом штормовом окне, плато
  7.0–7.1G до конца прогона (peak=current); не коррелирует ни с сущностями
  (+69 трупов за окно), ни с долгом (owed уже 0). Отложен в
  docs/deepening-plan.md с триггером (жалоба владельца на память
  длительных сессий / воспроизведение в нормальной сессии): разрез
  heap-гистограммой по методу №23 — отдельная работа; стационарные числа
  №23 (2.2–2.3G Париж) не опровергнуты — шаг случился только под голодом.

## Негативы, остатки и уроки (следующим звеньям)

- Soak на машине с живой агентской сессией contaminated по определению:
  каждый сэмпл/вызов модели = 1–3 мин CPU = волна голода. Осмысленны
  инварианты/консервация/восстановление, НЕ абсолютные скорости и спайки.
  Честный горизонт сим-времени — дельта SimClock между сэмплами, не
  SimSpeed.actual (окно усреднения + волновые отступания).
- vmmap-грепка: `grep 'Physical footprint'` — строки «Physical footprint:»
  и «(peak):»; старый паттерн `physical footprint|dirty` ловил мусор типа
  «unused but dirty shlib».
- `texts tick` матчит строку pathfinding-оверлея (в ней «, tick N»), а не
  третью строку панели скорости. Стоимость тика читать через `res get
  SimLoad` (registered: tick_ms/wait_ms/wait_peak_ms/frame_sim_ms/frame_ticks).
- failed% ответов pathfinding 0→27.6→17.3 под нагрузкой — не расследовался
  (in-flight ограничен, поиск здоров 0.04–0.72 ms avg); при желании —
  отдельный микропрос accept_answer/retire.
- Archetype census 1324→1339 за ~1.3 сим-ч — почти застыл; рост дают
  переходы поведения (новые комбинации компонентов), волны №33 не
  размораживают его существенно.
- worktree perf40 + ветка perf40 без коммитов (правок кода не было) —
  удалить (`git worktree remove .worktrees/perf40 && git branch -d perf40`).
- Повторяемый порядок soak: worktree-сид owner-view → ready → T0-сэмпл →
  `speed 30` → фоновый `sleep 240` → сэмпл (пауза→чтения→resume) → в конце
  vmmap footprint + гигиена лога.

## Вердикт по перфу

Правок кода нет — рантайм-цены не появилось; soak — наблюдение
устойчивости, не изменение. Замер до/после не нужен.
