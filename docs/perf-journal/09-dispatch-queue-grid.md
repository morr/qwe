# Запись 9 — Диспетчер заявок: скан мирных → сетка очереди; доминанта прохода — спавн тасков

Статус: фикс + вердикт. Файлы: `src/movement/pathfinding.rs` · `src/movement/mod.rs` ·
`src/movement/tests.rs` · `examples/bench/dispatch_bench.rs` ·
`navigation-deep/references/pipeline.md` (1bc820b3, 91bcf0df).

**Кандидат.** Живой диспетчер каждый кадр перебирал *все* стоящие мирные
заявки (в шторме 17–19k) гейтом видимости — неархетипный проход по всей очереди за то,
чтобы выбрать видимых.

**Фикс — сетка очереди.** `SpatialGrid<QueuedWander>` ведётся
четырьмя наблюдателями жизненного цикла заявки (встала → в сетке; UrgentPath, снятие,
despawn → из сетки), тот же принцип event-completeness, что у `DestinationClaims`:
порядок снятия пары не гарантирован, каждый наблюдатель чинит противоположную сторону.
Диспетчер берёт мирных `for_each_in_rect` кадра вместо скана очереди. Инвариант,
на котором всё держится: стоящая мирная заявка неподвижна — она не ходит за пешкой, а
диспетчер читает позицию живьём, сетка решает только *кого* читать. Детерминированный
диспетчер не тронут (replay-контракт).

**Бенч.** Перезапускаемый офлайн-бенч диспетчера (`dispatch_bench`):
полный `World` без окна, персистентный инстанс системы на
`run_without_applying_deferred` — команды не применяются, итерации видят одну и ту
же очередь. Методика честного замера выстрадана: OOB-тайлы опустошают пул и надувают цену
спавна в разы (каждый спавн будит поток), поэтому в замере настоящие поиски — насыщенный пул
как в игре; при насыщенном пуле вытеснение даёт шум p95 — *сравнимы фазы, не тоталы*.

**Числа фаз** (шторм 20k очереди, зум крупный/широкий): скан мирных
110–170 → 28 мкс (4–6×), на широком 89 → 2 мкс (45×); сборка из сетки 20–90 мкс, ~2 мкс на
широком.

**Главная находка развёртки фаз: скан был не доминантой.** Проход диспетчера
в шторме держат два места, оба не тронуты этим фиксом: **цикл спавна тасков** —
`AsyncComputeTaskPool::spawn` будит поток пула на каждый таск, 0.5–1.7 мкс/спавн
при простаивающем пуле (дешевле в насыщенный), 0.4–1.3 мс/кадр при 712–1024 диспатчах — и
**сорт кандидатов** ~160 мкс при переполнении бюджета (~6000 кандидатов →
truncate до 1024). Это кандидаты следующего заезда (см. ниже, очередь планировок).

**Живая проверка** (20×, шторм, 17785 пешек, 1998 убитых, caffeinate): тик
0.20–0.21 мс на всех трёх зумах, pathfinding 0% failed, 0 паник; мирных, стоящих в очереди
внутри прямоугольника диспетчеризации, — 0 (разбирается за кадр); на широком зуме (0.91 >
отсечки 0.75) мирных в кадре 157 — ждут по дизайну, срочные при этом диспетчатся. Скриншоты
трёх зумов — без регрессий картинки.
