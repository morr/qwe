# Deepening plan — решения архитектурного обзора 2026-11-16

Источник: глобальный обзор (7 зон, отчёт-артефакт `qwe-architecture-review` в проекте `qwe`
на сервере артефактов). Каждый пункт: вердикт, форма углублённого модуля, первый шаг,
скиллы, которые грузить реализующей сессии. Термины новых модулей (`BuildingClass`,
`CityContext`, `TickStage`, `Census`) входят в `CONTEXT.md` и в скиллы только вместе с кодом,
который их несёт — по правилу VISION/CLAUDE.md о двух уровнях документации.

Порядок выполнения (не порядок карточек): №1 → №3 → №2 → №7 → №6 → №4 → №8/№5 по триггерам.
№1 и №3 независимы, могут идти параллельно.

## 01 MapData — из сумки из 30 Vec в модель с запросами · ДЕЛАЕМ

**Форма.** Решётка предикатов на `RoadLine` (model/roads.rs) — каждое понятие названо и
задокументировано там, где уже живут `is_carriageway` (мост — тоже проезжая часть) и
`carves_navmesh`:

- добавить `is_at_grade()` = `Street && !bridge && !passage` и свести на него
  `rail.rs::crossable` и **две** инлайн-копии в `parking.rs` (174–177 и 233). Заодно решить
  расхождение: rail/parking не проверяют `highway.is_street()`, модельная решётка —
  проверяет; либо это дрейф (добавить проверку), либо замысел (задокументировать почему);
- `is_footbridge` (footbridge.rs) и `is_approach` (rings.rs) — другие понятия, остаются
  локальными: названы, у каждого ≤2 читателя;
- запросы на `MapData` заводить только для фильтров с ≥2 потребителями (улицы для
  rail+parking; пере-матчинг `AreaKind` в spawn.rs → итераторы по видам);
- `None`-поля решает модель, а не потребитель: accessor `lanes()` считает от ширины, когда
  поля нет; аналогично pavement, если такой случай есть;
- raw-режим: один предикат модели («сгенерированный контент есть») вместо шести веток
  `map.knobs.raw.draws_raw()` в потребителях;
- проверяющий конструктор — **отложено**: ручные тестовые карты зависят от слабого
  конструктора, валидация — отдельная работа с собственным планом.

**Тесты.** Предикаты решётки — таблицей в tests у model/roads.rs; запросы модели тестируются
на существующих парс-фикстурах. **Скиллы:** `osm-map`, `bevy`.

## 02 BuildingClass — классификация здания один раз · ДЕЛАЕМ, два шага

**Форма.** Шаг 1: `buildings/classify.rs` — `classify(building) -> BuildingClass`, единственный
match по `building_use` × размеры × пороги; таблицы высот, палитры стен/крыш, этажность и
clutterswitch на класс. Сначала сводим drifted-пару heights+material (условия уже разошлись),
затем layers/clutter. Шаг 2: `CityContext` — sanctuary, garage_runs, arches считаются один
раз в `mesh_buildings` и передаются билдерам (сейчас `Sanctuary::of` ×5, garage_runs ×3).
Flat-режим: общий шаг `HouseLook`, один match `Roofing` (сейчас два, разошлись условия
дымоходов); extrusion-сборка — общий случай, flat — её вырожденный случай без подъёма.
`temples → Option<SacredPlan>` — третьим шагом, после того как классификатор станет входом
(сейчас семь боковых дверей из пяти файлов) — **отложено** (deep02, 2026-11-17:
классификатор стал входом, но шаг не в этом заезде — запись только в архиве
NOTES). Триггер: следующая правка temples/Sanctuary-дверей или восьмая боковая
дверь.

**Тесты.** Таблица соответствий «здание → класс»; приватные тесты tests.rs переезжают на
классификатор по мере того, как их приватное становится его входом; тесты `mesh_buildings`
не меняются. **Скиллы:** `osm-map`, `bevy`.

## 03 TickStage — порядок тика списком · ДЕЛАЕМ (дешёвый, аддитивный)

**Форма.** Новый модуль (не в sim_time.rs — он уже толстый): упорядоченный перечень сетов
стадий — guard → tick → snapshot/answers → spawner → demon grid → demon behavior → human
behavior → move → separation → dispatch. `configure_sets(...).chain()` в одном месте
(SimBootPlugin/sim_yard), плагины кладут системы в сет стадии, `.before/.after`-рёбра между
плагинами исчезают. Регистрация `tick_probe` — циклом по тому же перечню: теневая копия
порядка в логгере умирает. Тест инспектирует расписание (порядок стадий) — форму API
инспекции расписания в 0.20 сверить по скиллу `bevy`.

**Миграция.** Аддитивная: ввести сеты, перевести рёбра на них, поведение не меняется.
**Скиллы:** `determinism` (SimPipeline/сет заказа — его территория), `bevy`.

## 04 Реестр слоёв · ЧАСТИЧНО

**Делаем.** (a) `swap_layers(...)` — форма rebuild (despawn по тегу → mesh → spawn_layers →
report) в одно место, обобщение существующего `respawn_overlay`; ~12 копий исчезают.
(b) z-лестница с assert'ами переезжает из settings.rs в map-модуль (`map/z.rs`): это
инвариант карты, а не число, которое читают два модуля; settings.rs остаётся для
действительно общих чисел (MAP_SIZE, проекция, sim).

**Откладываем.** Дескриптор-реестр, выводящий обе цепочки из списка. Причина: цепочки несут
реальную семантику порядка (зависимости слоёв), выводящий макрос её прячет — шов без
второго адаптера. Триггер пересмотра: следующий добавленный слой — если снова 8 правок
вразброс, реестр оправдан. **Скиллы:** `osm-map`, `bevy`.

## 07 Census — счётчики один раз · ДЕЛАЕМ (с оговоркой по перфу)

**Форма.** Census-ресурс: per-state счётчики считаются **один раз за кадр** в Update перед
потребителями — не за тик (20 000 сущностей × каждый тик — так не надо); это строго меньше
нынешней работы, где HUD считает своим запросом каждый кадр, а диссектор спайков — ещё
семь состояний инлайн. `killed`/`escaped` остаются инкрементальными (уже события).
Потребители: HUD (`ui/stats.rs::sync_world_counts`), диссектор спайков (уходят 12
параметров и 8 опциональных запросов), Fingerprint реплея. Инвариант
`alive + killed + escaped == PopulationSize` — debug-проверка раз в кадр.

**Скиллы:** `species-behavior` (telemetry), `sim-speed` (диссектор), `determinism`
(fingerprint), `bevy`.

## 08 probe() — инспектор спрашивает слои · ОТКЛАДЫВАЕМ, после №1

Причина: дублирование инспектора — во многом следствие отсутствия запросов модели (№1):
z-константы, метки и модель ширин читают то, что модель должна отдавать сама. После №1
останутся labels/shapes — тогда и решить. Триггер: следующий инспектируемый признак.
**Скиллы (когда откроется):** `osm-map`, `bevy`.

## Обзор №8 — восьмой глобальный проход, 2026-11-19

Угол: пути отказа и тихие запасные значения + мёртвая публичная поверхность.
Мелкое ушло в фикс (дубль `#[cfg(test)]` на `sim_yard` в lib.rs); здесь — отложенное.

- **Мёртвая pub-поверхность: 89 item-ов** (`pub` без единого потребителя вне своего
  файла; 88 используются только в своём модуле, 1 — `rng.rs::seed_for` — ещё и своими
  тестами через `super::`). В lib-крейте rustc их никогда не пометит: `pub`-цепочка

## Обзор №15 — пункт меню (б) измерен, отложен: аллокатор неокупается, 2026-11-20

Полный A/B пункта (б) сделан (mimalloc v3, декоммит; чистая пара на Astar,
чередование, 3 прогона на сторону по 7 загрузок Тула↔Париж). Результат:
**не вливать** — выигрыш в пределах погрешности, в покое дороже, а «малой
правки» не существует.

- **Жёсткий факт: `#[global_allocator]` несовместим с `bevy/dynamic_linking`.**
  Rust-дайлибы (bevy_dylib) несут свой собственный System-аллокатор — атрибут
  бинаря на них не распространяется; любой Box через границу бинарь↔дайлиб
  (`Box<dyn System>` из `prefs::track_pref`, освобождаемый в bevy_ecs) падает
  с SIGABRT `BUG_IN_CLIENT_OF_LIBMALLOC_POINTER_BEING_FREED_WAS_NOT_ALLOCATED`.
  Рабочая форма одна — interposing malloc всего процесса (DYLD_INSERT_LIBRARIES
  с shared-сборкой mimalloc v3; статическая не interpose-ит дайлибы из-за
  two-level namespace). Патч с атрибутом лежит на ветке `perf15`
  (worktree `.worktrees/perf15`); dylib и рецепт запуска — в NOTES master.
- **Замер (Париж→Тула↔Париж×3, footprint `vmmap` + ps rss):** вставка выводит
  footprint на плато сразу (Париж 2.3G, Тула 1.7G — без роста по серии), но
  платит в покое с первой же загрузки: S0 Париж 2.1–2.3G против 1.8–1.9G у
  системного (ps 3.26–3.28G против 2.64–2.65G, стабильно три прогона).
  Базовый рост сам замедляется (Тула 2.66→3.15→3.48G; №12: +270→+50), к концу
  серии итоги сопоставимы (3.47–3.48 против 3.54–3.74 ps). Чистый выигрыш
  появляется только после многих переключений и ≈ 0–0.4 ГБ за час
  переключений; на короткой сессии — чистый минус.
- **Тик/кадр/джерки:** регрессии не видно и выигрыша тоже (разрешение ±5 %):
  throughput на speed 30 — base 6.1–6.6x (среднее 6.28), вставка 5.8–6.5x;
  спайки 327–440 против 372–469; окна загрузки не изменились (Париж тёплый
  4.48–4.75 с, Тула 1.19–1.27 с). check.sh (build + 1587 тестов + clippy +
  fmt) под атрибутом зелёный; приложение под вставкой стабильно — 3 полные
  серии и тиковые шторма, ноль паников.
- **Триггер пересмотра:** жалоба владельца на память ДЛИТЕЛЬНЫХ сессий
  (часы и много переключений) — тогда выбор между interpose-шиммой в бинаре
  (C-таблица `__DATA,__interpose` + dylib-зависимость), отказом от
  dynamic_linking с простым атрибутом (дороже итерация dev-сборок) и
  opt-in-запуском через DYLD_INSERT (нулевого риска, рецепт в NOTES).
- Побочная находка той же серии: при `PathfindingAlgorithm=Astar` тёплый
  вход Парижа иногда ловит `warmup timed out with 9 pawns` (фоллбек
  WARMUP_TIMEOUT, мир продолжает) — дефолт Hpa не затронут.

Уроки замера: `$b ready <log>` ищет маркер по всему логу — после первой
загрузки он мгновенно «готов»; для серий переключений ждать НОВУЮ строку
warmup (счёт до/после). Параллельная компиляция (check.sh) на 10× замедляет
загрузки и тики — живые замеры только при пустой машине; `algorithm=Hpa`
в сохранённых настройках запускает сборку northstar (22–28 с) после каждого
входа в Live — для серий переключений ставить Astar.

рода: ленивый старт постройки из `Update` (`navigation/mod.rs`, по смене

детерминизмом переключение на панели запускает постройку, которой замороженный
прогон не читает, а следующий рестарт заморозит уже `Backend` с иерархией:
два прогона одного сида на разных бэкендах. Рецепт: под детерминизмом заказ
рестарта ждать, пока `mode().is_building()` (условие на клавише и в
`trigger_pending_restart`; старый прогон просто дотикает), ленивый старт
убрать в `SimPipeline::Live`. **Триггер:** детерминированные повторы как
рабочий инструмент (приёмка, реплеи) либо жалоба «под детерминизмом рестарт
пошёл иначе».

1.5 км отвечают NO PATH. У Берлина хинт тоже вне меша: ближайшей свободной точки в
допуске нет, три пробы из четырёх вне меша. Всё три города одинаковы до и после фикса
№76 (проверено прогоном примера на меше до правок — `build.rs` спрятан сташем на время
прогона). Аудит смотрит на сырой хинт, а
игра его снапает по сетке (`snap_portal_position`) — что происходит в Ростове на самом
деле, не проверял. **Триггер:** следующий прогон `polymesh_start_area` по всем городам
либо первая жалоба на старт в Ростове/Калуге/Берлине. Рецепт: пропуск города без кеша со строкой в
выводе; вторая колонка вердиктов — после снапа портала тем же кодом, что в загрузке.
Область — `navigation-deep` (`examples/audit/polymesh_*`).

### 4. Полный аудит паритета «сетка против меша» существовал один прогон как TEMP-зонд

Классификация всех центров тайлов города по правилам заливки (12 с Тула, 38 с Париж —
отладочная сборка, кеш города обязателен) жила в `navigation::navmesh::temp_audit` и
удалена до коммита: она звала `pub(super)`-хелперы растеризации, которых примеру не
видно. Держат её итог только пины на `tiny_city` — по одной зоне на класс правила — и
таблица в `references/polymesh.md`. **Триггер:** правка любого списка в постройке меша
(`blocker_shapes`, `carve_contours`) или порядка `fill_base`, после которой «сетка и меш
сошлись» доказывают на глаз. Рецепт: `examples/audit/polymesh_parity_audit`, который
растеризует правила заново на центрах тайлов своей маленькой версией `set_polyline`
(капсула + цепочка, ~100 строк), либо `#[cfg(feature = "audit")]`-окно в `navmesh` для
трёх хелперов. Непрочитанный остаток того же аудита — 83 тайла в Париже и 22 в Москве
класса «дом без прорези» (центр тайла — под домом, ни настил, ни примыкающая дорога его
не кроят; расхождение по классам не разложено): догадка — внешний угол ленты на остром
угле против капсульной заготовки аудита; не проверено.

### 5. Срезанный торец водотока у входа в трубу не закреплён ни одним пином

Свободный торец ручья и оба торца стены закреплены (`a_free_stream_end_is_round_in_both_fills`,
`a_wall_blocks_in_both_fills`), а торец у кульверта — нет: `water_line_caps` срезает его
ровно в обеих заливках, но смена капа на круглый пройдёт все тесты зелёной
(`a_culvert_blocks_neither_fill` смотрит только на линию трубы, не на полширины русла за
торцом). Торцы оград в меше остались срезанными: в аудите они дали 0 тайлов (полоса ограды
0.3 м уже тайла), звено их не трогало. **Триггер:** правка `water_line_caps` или ширины
полосы ограды. Рецепт: проба на оси русла в полуметре за срезанным торцом (свободно) и
на полширины за свободным торцом того же ручья (заблокировано) — один тест на обе
заливки. Область — `navigation-deep`.

## Обзор №77 — отложено: стартовая площадка мира — три вопроса, 2026-11-23

Снято звеном №77 (ветка `start77`; аудит `polymesh_start_area` переписан под портал, с которым
играет загрузка, — кромка демонов, квадрат клиренса после калиток и прунинга, решётка 200 м по
центрам тайлов; TEMP-тест снапа по 13 городам на навтайлах 2 м и 1 м). Снятое на месте: хвост №76,
п. 3 — аудит смотрел сырой хинт, а игра портал снапает, и «старт вне меша» в Калуге, Ростове и
Берлине был артефактом аудита; отступ кромки демонов назван константой `PORTAL_RIM_MARGIN`, формула
квадрата клиренса вынесена в `navigation::portal_clearance_tiles`, пин
`the_snap_clearance_covers_the_demon_rim` держит связку «квадрат накрывает кромку» на обоих
навтайлах. К №65: решётка 200 м по 13 городам (13 832 центра тайлов, 10 688 свободны по сетке)
нашла одну точку, свободную по сетке, лежащую на меше и отрезанную от портала по мешу, — сад
частного двора за стеной в Париже (1301, 1301; вокруг дома и `barrier=wall` / `retaining_wall` /
`fence`); крупных отрезанных регионов нет, класс №65 — карманы размером с двор и меньше.
«Отрезано по мешу, но тайл закрыт и сеткой» — 0–25 точек на город (Ростов 17, Девилс-лейк 25):
карманы, которые исключили оба заполнения.

### 1. Восемь городов ни разу не прошли через снап портала

Кеша нет у Москвы (`moscow`), её юго-востока, юга, юго-запада и запада, Нью-Йорка, Лондона и Токио —
аудит пропускает их строкой, TEMP-тест тоже. По ним не проверено ничего из снятого по 13 городам:
находит ли снап место в пределах `PORTAL_SEARCH_METERS` (400 м; самый большой сдвиг из измеренных —
109 м, Калуга), чиста ли кромка, стоит ли снапнутый портал на меше. **Триггер:** первый запуск любого
из восьми — кеш скачивается при первом входе в город. Рецепт: `cargo run --release --example
polymesh_start_area -- 0.2 <slug>`. Область — `navigation-deep`.

### 2. Ветвь «нет чистого места» ни разу не исполнялась

Когда в пределах 400 м нет ни одного тайла с чистым квадратом клиренса, `snap_portal_position`
возвращает `None`, поток загрузки оставляет сырой хинт и пишет `no clear spot for portal` — мир
стартует с порталом там, куда его положил хинт, возможно внутри препятствия. Кромка демонов не имеет
своей проверки проходимости, её единственная гарантия — квадрат клиренса, так что в этой ветви залп
рождается где придётся и попадает либо под спасение после неудачного поиска, либо под безрезультатный
поиск. По 13 городам на обоих навтайлах ветвь не сработала ни разу. **Триггер:** первая строка `no
clear spot for portal` в живом логе. Решение за владельцем: расширять предел поиска, брать место
без полного квадрата или считать это ошибкой города и править хинт. Область — `world-lifecycle` +
`navigation-deep`.

### 3. Очаг волны и точки выпуска знает только сетка

`demon/horde.rs` берёт очаг волны и позиции выпуска по проходимости тайла — выбор с отклонением
непроходимых проб и запасным сканом, без меша и без квадрата клиренса. У портала проверок две:
квадрат по сетке и аудит по мешу. Сетка свободнее меша на кольце раздувания и в карманах, которые
меш отбрасывает при постройке, поэтому демон волны может родиться там, где по мешу стоит
препятствие, — и его поднимет спасение после первого неудачного поиска. Гипотеза, не измерялась:
живьём спасения волновых демонов отдельно не считались. **Триггер:** правка выбора очага либо
строка `rescued N entities` в первые тики после волны. Рецепт: офлайн-проверка очага и точек
выпуска тем же кодом, что в аудите портала (`nearest_free_point(p) == Some(p)` и путь от портала),
по одному городу с плотной застройкой. Область — `species-behavior` + `navigation-deep`.

### К1. Писатель позиции пешки · ДЕЛАЕМ

**Форма.** Новый модуль `movement/position.rs` — единственная дверь записи `SimPosition`;
`spatial.rs` остаётся стороной чтения. Три двери по виду переезда: шаг, телепорт (спасение,
смена яруса, рождение), толчок (расталкивание, бросок) — вид переезда и есть правило второй
точки интерполяции (шаг пишет точку на начало шага, стоящая пешка и телепорт сводят концы,
бросок — точку приземления). Писатель зовёт дверь в своей системе: жизненные события Bevy
0.20 (`Insert`/`Discard`) поднимаются только на вставку компонента целиком, а не на запись
поля; «событие + отдельная система» дала бы окно «пешка в мире, но ещё не в сетке» внутри
тика, где сетку уже читают захват и паника. `PawnEdit` (пять открытых полей, ноль
поведения) переезжает из `movement/components.rs` в модуль и получает поведение.

- **Закрытие на компиляторе.** У `SimPosition` и `PreviousSimPosition` убрать `DerefMut` и
  закрыть поле, `Deref` оставить: чтение `.0` по всему крейту не меняется, а запись
  `sim_position.0 = x` вне модуля перестаёт компилироваться. Change detection этих
  компонентов никто не читает (проверено: `Changed<`/`Ref<` по ним — ноль). Конструктор
  остаётся публичным для сайтов спавна (~32 построения в 13 файлах) — замена компонента
  целиком мимо двери остаётся возможной; задокументировать в модуле как единственную дыру.
- **Отчёт в сетку вида — обязанность двери.** Немедленный, когда писатель держит сетку;
  отложенный (накопитель, слив в конце той же системы), когда сетка держится общей
  ссылкой в обходе кадра (`assign_lod_tiers`). Привязка «вид → его сетка» регистрируется
  один раз: пара `Option<ResMut<SpatialGrid<..>>>` ×2 + `Has<>` ×2 уходит из пяти систем
  (`movement/systems.rs:118-123`, `:201-206`, `pathfinding/accept.rs:109-114`,
  `pathfinding.rs:473-487`, `:589-599`), `accept_answer` — с девяти параметров и
  `#[allow(clippy::too_many_arguments)]` (`accept.rs:84`).
- **Хвост шага** — одна реализация для ближнего шага (`movement/systems.rs:81-116`) и
  дальнего среза (`human/lod.rs:568-600`), по правилу ближнего (стоящая пешка сводит концы
  интерполяции): дальняя пешка невидима, а при возврате в кадр концы ставит смена яруса.
  Сегодня копии разошлись (`systems.rs:94-103` против `human/lod.rs:585`).

**Миграция.** Завести дверь → закрыть поле и переводить писателей по списку компилятора
(семь: шаг `systems.rs:98`, спасение `:150`, рождение `:265`, толчок
`separation/mod.rs:354`, дальний шаг `human/lod.rs:586`, спасение при возврате `:313`,
бросок `demon/behavior.rs:255`), один коммит на писателя → тест-двор → привязка видов.
Поведение бит-в-бит: что пишется и в какой точке тика — то же; отчёты остаются
синхронными там, где они синхронны сейчас (`TickStage::DemonGrid`/`DemonBehavior` читают
сетку тем же тиком).

**Тесты.** Тест-двор «шаг + расталкивание + спасение + смена яруса → сетка ≡ мир» по
образцу `tests/spatial.rs` (вторая половина рецепта №75.4) и тест двери на каждый вид
переезда (оба конца интерполяции и запись в сетке сходятся). Пины реплея и тесты
`behavior.rs` держат бит-в-бит. Аудит-флаг №75.4 остаётся отложенным со своим триггером.
Сегодня отчёт в сетку не проверяет ни один тест движения.

**Доки тем же изменением.** `CONTEXT.md` — записи `SimPosition / PreviousSimPosition` и
«every writer of `SimPosition` reports» переписываются с дисциплины на дверь; скиллы
`navigation-deep`, `species-behavior`. Закрывает отложенный пункт Обзора №2
«инкрементальность людской сетки» — его триггер сработал 21.11 (`human/lod.rs:313`,
`:586`; баг класса — 15f8235f). **Скиллы:** `navigation-deep`, `determinism`,
`species-behavior`, `bevy`.

### К2. Клеточное поле точечного слоя · ДЕЛАЕМ

**Форма.** Один модуль `silhouette/field.rs` с двумя адаптерами — дальний слой живых
(`FarCrowdField`, клетка 250 м) и трупное поле (`CorpseField`, клетка 500 м). Внутрь
уходят: запись клетки, сущность меша клетки (создание, замена, удаление), проход
перестройки с бюджетом, правило «границы меша нельзя считать из вершин», швы жизни (оба
пути `WorldStarted`, выход из `Playing`), общий материал и `chunk_mesh` (переезжают из
`bake.rs`; `CorpseQuad` перестаёт называть общее понятие именем одного из адаптеров —
дальняя живая точка собирается как `CorpseQuad`, `far.rs:313-323`). Адаптер отвечает
только за четыре параметра шва: откуда квады клетки (хранятся в поле или читаются из
мира), единица бюджета, что делать на старте мира (очистить или перечитать), отсечение.

**Первый шаг — без смены поведения:** обе единицы бюджета (4 чанка за кадр, `bake.rs:68`;
12 000 квадов с кольцом догона, `far.rs:61`) и оба способа отсечения (выключено против
честных границ) сохраняются как есть — унификация «на глаз» либо мигнёт городом, либо
вернёт ловушку ложных границ (7e8b376c → c9c0f9b7). Живая сверка по `live-app`. Оба поля в
`SimPipeline::Live`, без RNG — детерминизму не мешает; новых проходов в кадр нет.

**Тесты.** Одна матрица жизни «путь старта мира × жива ли сущность меша × опустела ли
клетка» в тестах модуля; адаптеры — только на своём. Сегодня два стенда (`field_app`,
`bake_app`) и несимметричные пины: четыре у дальнего поля, один у трупного; отсечение не
покрыто ни одним тестом, хотя ловушка ловилась живьём дважды — первый пин на него.

**Связь с №74.** Пункт 3 (трупное поле переживает сцену) закрывается первым шагом как
свойство модуля; пункт 2 остаётся отложенным со своим триггером; дайджест для пункта 4 —
если поле отдаёт его бесплатно. **Скиллы:** `bevy`, `species-behavior`, `world-lifecycle`.

### К3. Лестница человека — одно применение на два яруса · ДЕЛАЕМ, после К1

**Форма.** Один механизм переходов (войти в панику, шаг бегства, успокоиться, выбрать
цель, проверить спасение); два вызывающих — ярусы, они различаются только темпом (каждый
тик или раз в `FAR_SLICE_TICKS` с `dt × K`), маршрутом (`request_wander_path` против
`direct_path`) и срочностью (`UrgentPath`). Образец в проекте — `acquire_pass` у демонов
(`demon/behavior.rs:34-105`). Сегодня применение лестницы написано дважды: 224 строки по
обе стороны, 44 различаются текстом; сбор паники — 17 = 17 строк, ноль различий
(`human/behavior.rs:62-80` ↔ `human/lod.rs:644-660`). Побочные действия смены яруса
(спрайт, оба конца интерполяции, срочность, отчёт сетке) — одна операция перехода; её же
зовёт `to_corpse` (`human/corpse.rs:442`, `462`); отчёт сетке — дверь К1.

**Первый шаг — характеристический пин на нынешних двух копиях:** та же пешка (тот же
`PawnId`) в обоих ярусах делает одинаковые броски. Красный на текущем коде — находка для
владельца (какая сторона права), объединение ждёт его слова; зелёный же держит бит-в-бит
при объединении.

**Ограничения.** Ближняя ветка — дословно: она идёт в детерминированном прогоне
(`a_restart_replays_the_run`, шесть тестов `behavior.rs`). Порядок бросков
`WanderIndex::next` не меняется; точка синхронизации после `far_onset` и
`chain_ignore_deferred` дальней цепочки (`human/mod.rs:237`) остаются. Лестницы человека и
демона не сливаются.

**Последний шаг — срезы.** Один механизм «разложить по N срезам и гонять систему по
срезу» с двумя адаптерами (`FarSlice`, 8 срезов; `DemonSlice`, 4) и одним пином
регистрации вместо двух ручных перечней (`human/mod.rs:212-235`, `demon/mod.rs:140-151`);
вставка маркера написана трижды (`lod.rs:124-136`, `demon/systems.rs:222-229`,
`lod/tests.rs:55-64`). Маркеры остаются своими: время жизни среза у видов разное по
задумке.

**Тесты.** Кросс-ярусный пин; повторные пины `lod/tests.rs` (`:494`, `:525`) превращаются
в тесты различий яруса. **Скиллы:** `species-behavior`, `determinism`, `bevy`.

### К4. Дорога входит в мир одним хвостом · ДЕЛАЕМ

**Форма.** Один «въезд дороги» в `map/roads/adopt.rs` по образцу `trees::adopt_trees` и
`buildings::spawn_building_meshes`: ему отдают дорожную сборку, то, что в руках (все
ступени / одна / недостающая), и то, что она заменяет (ничего / всё с `RoadLayerTag`);

**Тесты.** Один пин на фикстуре с тремя исходами: после входа обе ступени на месте, видима
одна, ресурсы — текущей ступени; после пересборки одна ступень, ресурсы свежие; после

### К5. Диапазон ручки · ДЕЛАЕМ

**Форма.** Диапазон — свойство ручки: поля группы настроек закрываются, чтение идёт через
аксессор, запись через сеттер, оба подрезают. BRP и файл добираются до полей через
отражение (производный код имеет право на закрытое поле) — оба пути записи работают, а
читатель больше не решает, защищаться ли. Отвергнуто «один проход подрезания при
применении настроек»: у записи по BRP нет крючка, между записью и проходом остаётся кадр,
когда мусор читает тик.

**Охват.** Три структуры плана ×10 — `DemonStyle`, `HordeStyle`, `HumanStyle`: 9 полей, 4
аксессора, 15 чтений без защиты (`demon/systems.rs:104, 237`, `demon/behavior.rs:179`,
`demon/horde.rs:204`, `human/systems.rs:40, 62`, `human/lod.rs:467, 667`), строки панели
(`ui/stats.rs:352-397`: `get`/`set`-замыкания переходят на аксессор и сеттер). Один
помощник вместо трёх форм аксессоров (17 аксессоров в 6 файлах) — в `prefs.rs`; диапазоны —
у полей, как уже требует правило CLAUDE.md. Остальные группы настроек — по триггеру
«следующая правка группы», не марафоном. Для честных значений поведение мира не меняется;
для мусора меняется — это цель (сегодня NaN в `speed` доходит до скорости демона).

**Тесты.** Одна таблица «мусорное значение → что прочитано» на механизм (сегодня четыре
разрозненных теста: `demon/components.rs:326, 357, 374, 398`). **Скиллы:** `bevy`,
`ui-panels`, `species-behavior`.

### К6. Состояние инспектора · ДЕЛАЕМ, два шага

**Форма.** Одно состояние в `ui/inspector/state.rs`: находки, выбор, окно, пины с цветами,
признак «включено», последний учтённый набор входов. Интерфейс — операции, которыми его
дёргают события (курсор пришёл или ушёл, входы изменились, листать вперёд и назад, пин
поставить или снять, стереть пины, переключить галочку, карта сменилась); ответ — что
показывать: строки списка с выбранной и хвостом, форму подсветки, пины. Системы — тонкие
адаптеры. Внутрь уходят «пин только при галочке» (8 проверок `enabled.0` в 6 системах),
окно за выбором (окно — `Local` одной системы, выбор — поле ресурса: одно понятие у двух
владельцев), стирание пинов при смене карты (сегодня делает система перерисовки).

- **Шаг 1:** состояние с операциями и тестами, системы зовут его в прежнем порядке —
  «клавиши срабатывают тем же кадром» сохраняется по построению.
- **Шаг 2:** три ручных перечня «когда пересчитывать» (`inspector.rs:539-543`, `:919-925`,
  `:1015-1021`; всего 18 `is_changed()`) схлопываются в сравнение набора входов целиком.
  Меняет перерисовку — живая сверка цены кадра по сценариям звеньев №66 и №68.

Слои подсветки не трогаются (`surface::swap_layers` уже углублён). Файл в списке
diet-плана (53.5K) — состояние естественная первая граница разреза.

**Тесты.** Через состояние без приложения: хвост «+N more» (сейчас проверяется на
`format_hits`, который панель не зовёт), выбранная строка всегда в окне, заворот листания,
цвет удерживается, пины стираются сменой карты, «ничего не изменилось — ничего не выдано»
(класс cb14bcd3), «любой вход изменился — пересчёт» (класс 57552628). Абзац скилла
`ui-panels`, написанный по именам систем, обновляется тем же изменением. **Скиллы:**
`ui-panels`, `bevy`.

### К7. Готовое из потока приходит с ключом · ШАГ 1 — ФИКС СРАЗУ; шаги 2–3 ОТКЛАДЫВАЕМ

**Шаг 1 — дефект (найден чтением, живьём не воспроизводился).** Поток строит полимеш под
панелью, снятой на старте (`loading.rs:328-331` → `prepare.rs:256-260`), а

Измени панель радиусом во время загрузки (запись по BRP) — меш, надутый старым радиусом,
получит штамп нового, `sync_polymesh_build` выйдет по `built_for == key`
(`polymesh/mod.rs:414`), и мир едет на чужой геометрии, под детерминизмом — замороженный на

`polymesh/mod.rs:333-337`). Фикс: ключ едет с артефактом — штамп той панели, под которой
