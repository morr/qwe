# Запись 18 — бинарный снапшот MapData: тёплый старт Парижа, парс 5.3 с → чтение 0.1 с

Статус: фикс заезда 08 (`planned/04-parse-speedups.md`, пункт 4b). Файлы:
`src/map/osm/snapshot.rs` (новый) · `src/map/osm/{download,overpass,model}.rs` ·
`src/map/osm/model/{features,roads,trees}.rs` · `src/map/roads/network/streets.rs` ·
`src/map/osm/{contours,parse}.rs`. Замеры: живой Париж, два базовых и три правочных
прогона в одном состоянии машины под `caffeinate -i` (`QWE_PERF_NOAPPNAP=1`,
`QWE_PERF_NOVSYNC=1`); до правки явной строки суммарного парса не было — она
замерялась между строками лога (кеш-хит → navmesh filled), после — строкой
`osm: parsed … of json in …`.

**Было.** Тёплый старт Парижа платил за разбор 160 МБ JSON при каждом запуске:
5.29–5.36 с чистого парса, 5.53–5.55 с вместе с чтением кеша (строки
кеш-хит → navmesh filled) — после записи 14 крупнейшая последовательная часть
до мешинга. Спека 4b предполагала сотни МБ на диске; опасение не оправдалось.

**Правка.** `map/osm/snapshot.rs`: сериализованный `MapData` (bincode 1.3,
serde-дерейвы по модели, фича `serialize` bevy — под `glam/serde` у `Vec2`)
пишется в поток загрузки сразу после успешного разбора (40 МБ за ~68 мс) и
читается **вместо** разбора при тёплом старте. Жизненный цикл — как у
JSON-кеша: пишется только после успеха, битый удаляется и мир разбирается
заново (самолечение). Инвалидация двумя слоями:

- **имя файла** — имя JSON-кеша минус `.json` (слаг, гео-центр, размер карты,
  `QUERY_VERSION` наследуются) + `s{SNAPSHOT_VERSION}` (форма снапшота) +
  `k{lane_width}_{navtile}_{raw}` (входы разбора). Номер формы растёт при
  любом изменении того, что разбор кладёт в `MapData` — дисциплина
  `QUERY_VERSION`: имя не видит правку разбора, а устаревший снапшот
  **декодируется молча**, ошибкой это не ловится;
- **заголовок** — размер и mtime JSON-кеша, под которым снапшот писался:
  перекачанная выгрузка под тем же именем (задокументированный способ
  обновить карту — «удали кеш, запустись заново») инвалидирует снапшот.

`prune_stale_caches` метёт устаревшие снапшоты тем же правилом, что кеши:
под слагом города выживает только актуальный — текущих входов разбора.

**Контракт детерминизма** — два уровня:

- юнит-тест `snapshot_gives_the_same_map_as_parse`: сцена-фикстура через
  настоящий `parse` → encode → decode → равенство (`PartialEq` добавлен
  модели);
- на живом Париже строка `osm map:` (56188 зданий, 86243 входа, 69419 дорог,
  31002 деревьев) совпала бит-в-бит во всех прогонах — и на парсе, и на
  снапшоте, и после цикла туда-обратно по входам.

**Замеры** (Париж, тёплый json-кеш, одно состояние машины; шум межпрогонный
±8–15 % — здесь почти не виден):

| фаза | до (2 прогона) | после (снапшот-хит, 2 прогона) |
|---|---|---|
| разбор карты (парс + чтение) | 5.55 / 5.53 с | **0.097 / 0.099 с** (чтение снапшота) |
| чистый парс (строка `osm: parsed`) | — | 5.29 / 5.36 / 5.12 с на прогоне записи |
| navmesh fill (контроль) | 0.271–0.282 с | 0.273 / 0.282 с |
| мешинг до `osm map:` (контроль) | 9.79 / 9.90 с | 9.62 / 9.61 с |
| warmup (контроль) | 3.45 / 3.39 с | 3.42 / 3.46 с |
| кеш-хит → warmup done | 18.79 / 18.82 с | **13.32 / 13.67 с** |

Разбор карты **5.54 → 0.098 с (−98 %, −5.4 с)**; тёплый старт до играбельности
18.8 → 13.5 с (−29 %) — остаток держит мешинг (~9.6 с стены) и шторм warmup
(~3.4 с), они не парс. Запись снапшота на прогоне без снапшота стоит 61–73 мс
поверх парса — шум.

**Проверено живым** (одно приложение, BRP):

- инвалидация по входам: `res set RawOsm . '"Parse"'` → перезагрузка — снапшот
  `_k3.3_2_off` выметен prune-ом, разбор прошёл (raw-режим, 1.45 с), записан
  `_k3.3_2_parse` (35 МБ); обратно `"Off"` — `_parse` выметен, полный парс
  5.36 с, счётчики вернулись бит-в-бит;
- самолечение: обрезанный до 1 МБ файл → `osm: snapshot rejected (corrupt: io
  error: failed to fill whole buffer), falling back to json — removing …` →
  парс → перезапись, файл восстановлен байт-в-байт по размеру.

**Цена и границы.** Память: при чтении снапшот держит `MapData` целиком — как
парс, без промежуточного буфера (десериализация из `BufReader`). Диск:
+40 МБ на город/входы (Париж) против 167 МБ JSON. Механика не ускоряет ни
мешинг, ни warmup, ни первый запуск города (там парс неизбежен и добавляет
70 мс записи). `city_extract` витрины дорог снапшот не читает — её вход по-прежнему
JSON.

**Что дальше.** Очередь прежняя (запись 17): kerb_returns поузлово (запись 14,
~300 мс), мешинг-стена старта (здания ~8 с, тени 3.0 с — запись 14 «Что
дальше»; вход в мир ещё и заборы ~2.4 с в кадре под лоадером — запись 17,
кандидат на тот же перенос в поток), рендер-сторона шторма (запись 15
«Отвергнутое»). После этого заезда парс в тёплом старте Парижа больше не
участвует: 13.5 с — это мешинг 9.6 с + warmup 3.4 с + спавн.

**Метод.**

- Прогон: `BRP_PORT=15703 QWE_PERF_NOAPPNAP=1 QWE_PERF_NOVSYNC=1
  QWE_PERF_FRAME_SPIKES=30 caffeinate -i cargo run`, фоном; готовность —
  свежая строка `warmup:` в логе (маркер `brp ready` ловит предыдущую
  загрузку).
- База снималась до правок в том же сеансе, два прогона; «после» — три
  (первый пишет снапшот, два следующих — хиты).
- Валидация инвариантов руками: RawOsm через `brp res set`, битый файл —
  `dd`-обрезка; артефакт равенства — строка `osm map:` в каждом прогоне.
- Формат сериализации: `Vec2` в glam — tuple struct из двух f32, в bincode
  ровно 8 байт; `Rgb = [u8; 3]` — нативно; приватные поля
  (`RoadNetwork.place/continuations`, `TreeSet`, `RowTrees`) дерейвятся на
  месте, в свой сериализатор не заворачивались.
