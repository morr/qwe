# Запланировано 02 — мешинг карты в поток загрузки + параллелизм по группам

Приоритет: **2** (после чанкования; чанки менять не должны — делать можно и первым).
Средний заезд. Контекст: запись 10, правило world-lifecycle «тяжёлое — в поток».

## Зачем

- Тёплый старт Парижа ~24 с, из них ~14.6 с — мешинг в `OnEnter(Playing)` на
  главном потоке (`map/mod.rs`, `WorldInitSet::Spawn` → `spawn_map`). Кадр перехода
  15.7 с (frame spike 15685 ms) ≈ мешинг 14.6 с + спавн популяции ~1 с; лоадер всё
  это время заморожен на последнем сообщении — прямое нарушение правила
  world-lifecycle: «heavy init belongs in this thread, not in `OnEnter(Playing)`».
- Слой-функции чистые (`MapData → Vec<LayerMesh>`, без ECS — `MaterialSpec`
  вместо handle ровно для этого) — спроектированы под вынос в поток.

## Дизайн

1. `LoadedWorld` (`map/osm/download.rs`) несёт собранные меши: списки `LayerMesh`
   по группам в текущем порядке спавна `spawn_map` (surface, roads ×2 шага,
   buildings, cars, wagons, fences, industry, rails ×5 бакетов, trees...).
2. В потоке — job-состояния с прогрессом по группам
   (`BuildingMeshes { group }`), лоадер показывает, чем занят.
3. `OnEnter(Playing)` — только спавн: `spawn_layers` по готовым спискам
   (спавну нужны `Assets<Mesh>` — это дёшево, копия вершин в ассет).
4. Polymesh — тоже в поток: он идёт после `fill_from_mapdata` в том же потоке;
   где сегодня живёт вставка `PolyNavmesh` — проверить, ресурс вставлять как
   сегодня (OnEnter), данные возить через `LoadedWorld`.
5. Параллелизм (второй шаг): rayon по независимым группам внутри потока —
   buildings (7.0 с) ∥ roads (5.4 с) ∥ polymesh (4.2 с) ∥ surface/rails/прочее (~1 с)
   → 14.6 с → ~7–8 с. Все читают один и тот же `MapData`, пишут в свои списки.

## Шаги и верификация

- До/после: тёплый старт Парижа по строкам лога (сумма и разбивка), лоадер живой;
  `world reload: N survived` — 0; живая игра и `tools/check.sh`.
- Первый кадр после Live без 15-с спайка (`QWE_PERF_FRAME_SPIKES=30`).

## Риски

- Порядок спавна групп и z — сохранить текущий порядок списков.
- Building-тени (i_overlay union) остаются в своей группе как есть — здесь
  они не делятся, только переезжают в поток.
- inspect-индекс (2 пересборки ~250 мс) остаётся в OnEnter — не доминанта.
