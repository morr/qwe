## Найдено (коммит 5c412368 — док-твины CONTEXT.md + world-lifecycle; правок кода угол не потребовал; проба на мастер-бинаре главного чекаута, worktree не заводился)

- **Декомпозиция холодного старта (Париж, снапшот-хит, серийный путь; два
  чистых прогона, spawn→Live 7.3–7.5 с):**
  - **бут spawn→AdapterInfo 1.22/1.40 с** — dyld (dynamic_linking) + сборка
    плагинов + wgpu adapter/device; qwe-кода там нет (его Startup — после:
    атлас силуэтов 46.7 мс). DYLD_PRINT_STATISTICS на macOS 26 мёртв (нет
    вывода) — делить dyld/движок можно только TEMP-врезкой в main.rs, рычага
    у qwe в этом срезе нет — не резано.
  - AdapterInfo→Loading 0.15 с (окно + Startup: атлас 46.7 мс).
  - Loading→whole set 3.55/3.83 с — известное: серийный префикс 0.48 с
    (снапшот 92–94 мс + fill 137.3/137.6 + gates 173–175 + prune 81.7/81.8 —
    базы записей 61–63 сходятся) + лейны 3.0–3.4 с (макс — дороги).
  - **рамка входа — кадр 2145/2271 мс** (StateTransition: печати отчётов
    потока + спавн мешей + первый GPU-аплоад ~20M верт) — территория записей
    12/23/57.
  - **прогрев: строка «routed in 2.19/2.32 s» = вся Warmup-фаза** = рамка
    входа + хвост раздачи ~0.1 с («типичные ~0.15 с» скилла — только раздача).
    Механика: Warmup начинается при входе в Playing, рамка входа идёт внутри
    фазы и попадает в `WarmupProgress.elapsed`; подача/диспетчер/приёмка
    видимых пешек живут в Update того же кадра — реальная раздача быстра
    всегда, расхождение «2.32 против 0.15» было не скоростью диспетчера.
  - **Детальные строки мешинга в логе — печати отчётов потока входом**
    («road meshing … in 2.6s» печатается после «whole set», duration —
    посчитанный в лейне; spawn_map/spawn_* показывают отчёты, SurfaceReport —
    Display-поле PreparedMeshes). Лейн-строки («map meshes: … in …») —
    потоковые, печатаются по завершении лейна. Таймлайн резать по лейн-строкам
    и строкам перехода, детальные — исторические длительности.
- **Вердикт: дефекта нет, правки кода не требуются.** Три куска старта —
  движок/dyld, записи 58–63, записи 12/23/57 — закрытые или чужие территории.
  Единственная находка — семантика числа прогрева; уточнена в док-твинах
  (CONTEXT.md «App lifecycle» + скилл world-lifecycle, коммит 5c412368).
  Перф-вердикт: код не менялся — цены нет, угол диагностический.

## Наблюдения и уроки (следующим звеньям)

- **Деградация приходит волнами, привязанными к активности собственной
  сессии** (ZCode Helper 51 % CPU): из четырёх запусков №2 и №4 деградировали
  (все шаги ×25–100 разом, потоки T в ps -M) при живом NOAPPNAP+caffeinate,
  №1/№3 — чистые с канарейками на базах. Канарейки-шаги (снапшот-рид ~92 мс,
  fill ~137 мс) различают мгновенно; деградировавший запуск — выкинуть
  целиком, не вычитая нагрузку.
- **loadavg на этом маке врёт**: 14-дневный аптайм показывал 150–160 при
  5 бегущих процессах и 85 % idle в iostat — здоровьем машины loadavg не
  мерить, только канарейками шагов загрузки (дополнение к уроку №31).
- Запускать бинарь напрямую нельзя — «dyld: no LC_RPATH's found»
  (dynamic_linking живёт только в окружении cargo run); якорь спавна —
  pgrep-поллер `until pgrep -x qwe; do sleep 0.02; done` с gdate (у BSD date
  нет %N), разрешение ~20–50 мс, достаточно.
- `started_load_count 63` в bevy_diagnostic — не qwe, это счётчик загрузок
  ассетов bevy_asset (Startup: атлас, шрифты, UI) — не находка.
- Оптимизационное меню по-прежнему пусто (продуктовые решения владельца:
  вариант-в заборов, vendor northstar). Следующему звену — свежий угол;
  взятые — в постоянном разделе.
- worktree/ветки за звеном нет (правки кода не было; док-правки и NOTES —
  в главном чекауте, как NOTES-коммиты всех звеньев) — удалять нечего.
