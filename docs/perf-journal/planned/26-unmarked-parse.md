# Запланировано 26 — непомеченный остаток парса: разрез стены и фикс

Приоритет: **1** — запись 37: непомеченный остаток parse-стены Парижа —
**≈0.8–1 с из 3.483 с** (стена живой пары заезда 27). Заезд 28. Платится на
первом прогоне города, после бампа `QUERY_VERSION` и при промахе снапшота
(парс при промахе кеша; снапшот `s2` после парса переписывается).

## Проблема

Parse-стена Парижа — строка `osm: parsed 159 MB of json in …`
(`download.rs::parse_logged`, после неё снапшот переписывается). Помеченные
фазы (записи 36/37): карманы 1.211 (corners 0.417 внутри), деревья 0.430,
дома-с-тротуаров 0.229, блоки-к-дорогам 0.192, footway-стороны 0.191,
скверы 0.136, входы 0.134, парковки 0.134, плюс мелкие помеченные
(выпрямление хвостов, сечения). Сумма ≈ 2.66 с — **остаток ≈0.8–1 с не
покрыт ни одной строкой `osm parse:`**.

Что в него входит по коду (`parse.rs`):

1. **serde-чтение JSON** — `serde_json::from_str` в `parse()` поверх 159 МБ.
   Модель `Element` (`overpass.rs`): на каждый элемент `kind: String` +
   `tags: HashMap<String, String>` — сотни тысяч маленьких карт и строк.
2. **Элементный цикл `read_elements`**: `driving_side` (скан всех элементов
   ради стран), на каждую ноду — 4 проверки тегов (`parse_entrance`,
   `parse_tree_node`, `parse_structure_node`, `parse_road_node`; большинство
   нод без тегов), ways — `parse_way`, relations — `parse_relation` +
   `assemble_rings`. `OsmContours::of` в конце — помечен.
3. **Непомеченные ступени `finish_parse`**: `Districts::new` перед
   тротуарами (сетка по всем домам), `attach_entrances`, утопленники,
   сшитые рельсы, вера, `compose_trees`. Помеченные без тайминга
   (`sidewalks`, утопленники, рельсы) в разрез тоже входят — одна общая
   картина.

## Направление — сначала разрез, фиксы по факту

Разрез (временные `eprintln`, снятые до коммитов, патч в `/tmp`), все
ступени стены в одном прогоне: serde (`parse()`), `read_elements`
(`driving_side`, цикл по видам элементов, contours), `finish_parse` —
каждая ступень, включая уже помеченные. Сумма кусков сверяется со стеной
(3.483 с базы) — расхождение указывает на потерянный кусок.

Фикс — **крупнейший кусок ≥150 мс**. Кандидаты (по коду, до разреза):

- **serde**: `simd-json` (новая зависимость — правка `Cargo.toml` отдельным
  решением); либо дешевеющая модель `Element` (`kind: String` → `&'static str`
  через enum, теги `HashMap` → `Vec<(String, String)>` с линейным поиском —
  карты тегов крошечные). Смена модели задевает шов среза
  (`crop.rs` пишет тот же формат обратно — Serialize-сторона обязана
  выдавать байт-в-бит тот же JSON), решать по разрезу.
- **элементный цикл**: ранний выход по пустым тегам у нод (большинство нод
  их не имеет), порядок проверок от дешёвой к дорогой.
- **`Districts::new`**: сборка сетки по всем домам — один `Districts` на
  все вопросы, строится на каждый парс один раз (уже так) — резать, только
  если разрез покажет ≥150 мс.

**Правило выхода** (заезд 28): если разрез покажет, что рычаг в
замороженных файлах, или весь непомеченный остаток не даёт куска ≥150 мс —
берётся следующая по рейтингу фаза (corners 0.417 внутри карманов — машина
`kerb_returns` с пином нарисованных вееров, запись 36), и это фиксируется
в этой спеке и записи 38.

## Ожидание и риски

- Цель: разрез закрывает непомеченный остаток именованными кусками; фикс
  снимает ≥150 мс стены — стена 3.483 → ≤3.33 с медианой живой пары.
  Обещать больше без разреза нельзя.
- Риски: **наборы данных парса не двигаются** — все строки `osm parse:`
  бит-в-бит (счётчики), снапшот байт-в-бит с базой. Если оптимизация
  неизбежно даёт FP-сдвиг (например, смена порядка операций в проекции) —
  `SNAPSHOT_VERSION` бампается тем же изменением, расхождение фиксируется
  в записи 38 с обоснованием эквивалентности (как в записи 36).
- serde-модель: десериализуемые типы остаются на std-хешере (`HashMap` под
  serde) — swapping в bevy-хешер здесь не механика, а смена контракта.
- Витрина дорог (`examples/demos/roads`) и `crop.rs` — читатели того же
  `OverpassResponse`: любое изменение модели обязано сохранить формат среза.
