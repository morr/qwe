# План ×10: 200 000 людей, ~3 500 демонов, 15–30×

Подготовка симуляции к населению ×10 с удержанием скорости 15–30× на крупном городе
(Тула/Париж). Каждая фаза — самостоятельное звено цепочки qwe: ворктри, `tools/check.sh`,
живые замеры по скиллу `live-app`, мир остаётся зелёным по реплей-пинам
(`a_restart_replays_the_run`, отпечатки населения, порядок `TickStage`).

## Решения владельца (дано, не обсуждаем)

1. **Демоны — «фон + орды»**: постоянный фон одиночек с поднятым капом + периодические
   волны-орды (очаг-район, затишья между волнами). Внутри орды — прежний индивидуальный
   chase с заявками (макс. 2 преследователя на жертву), без группового разума.
2. **Люди — камерный LOD**: вне экрана пешки живут дешёво (блуждание/бегство по
   направлению без поиска пути, решения реже), у камеры — полный AI. Только живой режим
   (`SimPipeline::Live`); детерминистический реплей — полный AI без камеры.
3. **Скорость**: 15–30× при 200k. Кап 30× — продуктовый предел, не поднимаем.
4. **Трупы вечные** (без распада и капа): свежий труп рисуется спрайтами как сегодня,
   затем фоновый пекарь запекает его в меш чанка (фиксированная сетка чанков) и деспавнит
   три сущности трупа — рост счётчика сущностей останавливается. Дальней слой точек
   трупы не рисует.
5. **Население — новый дефолт мира**: `HUMAN_COUNT` = 200 000 (решение владельца,
   2026-11-21). Всё, чему нужен маленький мир, вставляет свой `PopulationSize`:
   реплей-двор делает это и сегодня (64 пешки); приёмочный пример
   `determinism_replay` закрепляется на 20k явно — его время не растёт.
6. **Кап демонов — общий потолок живых** (решение владельца, 2026-11-21):
   `DemonStyle::cap` ограничивает демонов из всех источников; фон заполняет до капа,
   волна выпускает `min(wave_size, свободное место)`. При полном капе волны вырождаются
   в пустые затишья — принятый трейд. Механики ухода демонов нет. Дефолт капа
   350 → 3500, потолок слайдера расширяется соответственно.
7. **Запечённые трупы — «точечный материал»**: свой шейдер с полом `HUMAN_MIN_PX`
   и клампом по зуму (по образцу `surface.wesl`); материал общий с дальним слоем Ф5.
8. **Единый порог городского зума** 0.75 для всего: ярус LOD, дальний слой, сепарация,
   отказ wander-диспетчеризации — одна константа, один вопрос «экран показывает весь
   город?».

## Бюджет скорости — арифметика и якоря

Регулятор решает скорость как `S = 1000 · share / (64 · tick_ms)`; из замеренной пары
«тик Парижа 0.21 мс → affordable 22×» доля симуляции в кадре ≈ 0.30. Отсюда бюджет тика:

- **15× ⇒ tick_ms ≤ 0.31 мс; 30× ⇒ ≤ 0.155 мс** — на 200k пешек.
- Сегодня полная пешка стоит ~10 нс/тик (0.21 мс / 20k; раскладка: flee 0.06 > panic 0.02
  > move 0.01 > spatial 0.004). Бюджет на 200k — **0.75–1.5 нс/пешку/тик**: никакая
  поштучная работа дальних каждый тик не помещается. Вывод: дальние живут **срезами**
  (шаг раз в `FAR_SLICE_TICKS` тиков с dt = K·тик) и без побочных поштучных проходов.
- «Хвост» тика ~0.15 мс вне сегментов — состав (сепарация на кадр, плауны конвейера)
  разложить замером в Ф1: при цели 30× он один съедает почти весь бюджет.
- Поштучные проходы, которые сегодня незаметны, а на 200k становятся лимитером:
  - `interpolate_movable_transforms` — 0.15–0.3 мс на 20k **за кадр** (замер в коде);
    на 200k это 1.5–3 мс/кадр. Дальние обязаны из него выпадать.
  - `check_visibility_cpu_culling` (bevy_camera 0.20) — O(n) по всем сущностям с
    видимостью, **включая скрытые**; `queue_sprites` фильтрует по `RenderVisibleEntities`
    (скрытый спрайт не попадает в фазу/сортировку/инстансы — проверено по исходникам
    0.20.1), но O(n)-проход видимости и реактивный `SyncToRenderWorld` остаются.
  - `resize_silhouettes_on_zoom` — O(n) чтений по всем силуэтам на кадр движения камеры.
- Рендер на 20k спрайтов уже лимитирует кадр при полном отдалении. Трупы не растут в
  сущности дальше «свежих» (запекание, Ф3), но 200k живых спрайтов на городском зуме
  всё равно не помещаются в кадр — дальний слой живых (Ф5) — условие играбельности.

Чего в бюджете **становится легче**: дальние не подают заявок поиска пути совсем —
давление на пул и `wait_ms` регулятора падает на порядки; лимитер смещается в CPU тика.

## Словарь новых терминов (предложение; в CONTEXT.md входят вместе с кодом)

| Термин | Смысл | Где живёт |
|---|---|---|
| **Камерный ярус** (Near/Far) | у камеры — полный AI и спрайт; далеко — дешёвое поведение и точка дальнего слоя. Правило границы то же, что у диспетчера (`waits_for_camera`, `VIEW_MARGIN`, зум 0.75), плюс гистерезис и выдержка | `human/lod.rs` (новый модуль) |
| **Срез дальних** (`FAR_SLICE_TICKS` K=8) | дальняя пешка делает шаг (и решает) раз в K тиков, срез фиксирован `PawnId % K` — детерминирован и не зависит от порядка обхода | там же |
| **Прогулка напрямик** | политика дальнего блуждания: точка в конусе курса, путь — прямая (`line_of_sight` по сетке), без заявки на поиск | `human/lod.rs` |
| **Запекание трупов** (пекарь) | осевший труп (кровь доросла) дописывается тремя квадами в меш своего чанка и деспавнится; «свежие» остаются спрайтами | `human/corpse.rs`, `silhouette/bake.rs` (новый) |
| **Трупный чанк** / `CorpseField` | меш запечённых квадов на ячейке фиксированной сетки; ресурс-хранилище квадов — источник правды для перестроек | `silhouette/bake.rs` |
| **Точечный материал** | общий `Material2d` трупных чанков и дальнего слоя: атлас + цвет вершины + разворот квада из «центр + полуразмер + пол» с клампом по зуму | `assets/shaders/` по образцу `surface.wesl` |
| **Дальней слой** (`FarLayer`) | чанковый меш точек живых дальних людей (демоны остаются спрайтами — их 3 500, ореол и блум сохраняются) | `silhouette/far.rs` (новый) |
| **Орда / волна / очаг / затишье** | волна = выпуск N демонов вокруг очага (случайная проходимая точка) за T секунд; затишье — пауза до следующей волны | `demon/horde.rs` (новый) |
| **Происхождение демона** (`WarpOrigin`) | точка выхода (портал или очаг); блуждание «от происхождения» — обобщение нынешнего «от портала», для порталальных демонов бит-в-бит то же | `demon/components.rs` |
| **Партионный спавн** (`SPAWN_BATCH`) | расселение 200k порциями за несколько тиков/кадров; порядок порций — тот же последовательный `0..count` | `human/systems/spawn.rs` |

## Фаза 1 — Спавн 200k партиями

**Файлы**: `human/systems/spawn.rs` (ядро), `loading.rs`, `restart.rs`, `census.rs`,
`tests/determinism.rs`.

**Механизм**. Сегодня `spawn_population` (482.8 мс флеша на 20k ⇒ ~5 с на 200k одной
рамкой) — одна команда `OnEnter(Playing)`. Той же фазой `HUMAN_COUNT` становится
200 000 (решение владельца №5): каждый стенд с маленьким миром закрепляет свой
`PopulationSize` (реплей-двор уже делает это; `determinism_replay` — закрепить 20k
явно в этой же фазе). Меняем на насос: `PopulationSpawn::spawn`
перестаёт спавнить сам и вставляет ресурс `PendingPopulation { count, cursor }`;
система-насос спавнит по `SPAWN_BATCH` (≈20k) сущностей за вызов, сохраняя
последовательность `0..count` и все броски потоков (`Population` — размещение,
`decision_stream` — личное) нетронутыми. Размещение (rejection-sampling) дёшево против
флеша сущностей и считается на первом вызове насоса; вынос на load-тред — только если
замер покажет пользу. Насос живёт:

- **в детерминированном прогоне — в `FixedUpdate`** (`SimPipeline::BothModes`,
  `.before(TickStage::Tick)`): партионность привязана к тику, не к кадру — число
  сущностей на данном тике не зависит от fps, иначе `a_restart_replays_the_run`
  расходится на разном железе;
- **в живом прогоне до входа в `Live` — в `Update`** (Warmup): `FixedUpdate` на паузе
  прогрева, а `poll_warmup` ждёт заявок от пешек в кадре — население должно существовать
  и подавать заявки, пока мир стоит. Симуляции в прогреве нет, кадрозависимость спавна
  траекторию не меняет; после `Live` живая половина насоса продолжается в `Update`
  (живой режим реплеем не заявлен).

`poll_warmup` не меняется: заявки появляются по мере прилёта партий, `WARMUP_GRACE`
покрывает первые кадры. `WorldStarted` не затронут (объявляется на входе в `Live`).
Рестарт (`restart.rs::on_restart`) идёт через тот же `PendingPopulation` — деспаун сцены
там уже случился до вставки ресурса, насос поднимет население заново. **Инвариант
переписи** `alive + killed + escaped == PopulationSize` проверяется раз в кадр — пока
насос не закончил, добавить к левой части `pending.remaining()` (или гейтить проверку на
«насос пуст»); иначе debug-ассерт падает на каждом кадре расселения.

**Детерминизм/реплей**. Пин «партиями == не партиями бит-в-бит»: маленький N (например
500), два прогона — `SPAWN_BATCH = N` (одна партия) и `SPAWN_BATCH = 50` (десять) —
отпечатки населения совпадают. Существующие `population_is_a_function_of_the_seed` /
`different_seeds_give_different_populations` остаются зелёными. Реплей-двор (64 пешки)
проходит тот же насос — пара тиков, поведение то же.

**Риски**: кадрозависимость живого спавна (закрыто паузой прогрева и «живой режим не
заявлен»); память сущностей 200k (замерить dirty footprint; к трупам — Ф3).

**Замеры** (live-app, Тула и Париж): рамка входа в мир по таймстемпам лога (база —
482.8 мс/89.6 мс флеша, запись 23), окно прогрева, `entities` телеметрии, `res get
SimLoad` на 200k при зуме внутрь города (сим-цена наивного населения — точка «до» для
Ф2); разложить «хвост» тика 0.15 мс по источникам (сегменты уже печатаются).

**Готовность**: 200k расселяется без рамки длиннее ~50 мс; прогрев сходится; инвариант
переписи зелёный на разгоне и после; реплей-пины зелёные.

## Фаза 2 — Камерный LOD людей

**Файлы**: `human/lod.rs` (новый: ярусы, срезы, дальнее поведение), `human/mod.rs`,
`human/systems/wander.rs` (фильтр яруса у `pick_wander_targets`), `human/behavior.rs`
(фильтры `panic`/`flee`, promote-хвост), `movement/systems.rs` (интерполяция),
`settings.rs` (пороги, если их читают двое).

**Механизм**. Ярус — архетипный маркер `FarTag` + постоянное значение `LodDwell(u8)`
(урок `PanicRecoil`: состояние — значение, не наличие; перенос архетипа только на самом
переходе). Назначение яруса — система в `Update`, `SimPipeline::Live`, запускается на
движение камеры (сравнение `Viewport` в `Local`, как у resize-прохода):

- **promote** (Far→Near): обход людской сетки прямоугольником кадра с запасом
  `VIEW_MARGIN` — O(живые в кадре), не O(население);
- **demote** (Near→Far): запрос архетипно `With<Human> Without<FarTag>` — только
  ближний набор (тысячи), проверка «вышел за кадр с запасом» + выдержка N тиков
  (`LodDwell`); гистерезис — тот же запас;
- **зум ≥ 0.75** (порог `wanderers_dispatched_at_zoom`, единый с сепарацией): Near пуст,
  весь мир — Far. Правило границы — одно, `waits_for_camera` (его единственная копия
  уже в `movement/pathfinding.rs`), LOD-модуль лишь спрашивает.

Дальний срез: `FarSlice0..K-1` (K=8, маркеры по `PawnId % K`, ставятся на demote,
снимаются на promote — K переносов на переход, переходы редки). Дальнее поведение —
системы в `FixedUpdate`, `TickStage::HumanBehavior`, `SimPipeline::Live`, каждая
запрашивает свой маркер среза (нулевой пропуск, никакого перебора 200k):

- **дальнее блуждание** (замена `pick_wander_targets` для дальних): на срезе, после
  паузы — та же политика stroll (`point_in_cone`), затем `line_of_sight` по сетке до
  цели: прямая видима — путь `[target]`, состояние `Moving` без заявки; нет — пеший
  ждёт следующего среза (переброс). Шаг — существующий `step_along_path` (остановка у
  непроходимого тайла уже в нём). Этажей-«дел» у дальних нет — только прогулка;
- **дальний onset паники**: на срезе `any_in_cells_around` по сетке демонов (O(1));
  переход в бегство — те же записи (`FleeRepath` с периодом ~K тиков), **без
  `UrgentPath` и без заявки**;
- **дальнее бегство**: та же чистая `decide` (пробы дешёвые), применение — вектор от
  угрозы, путь-прямая как выше; броски потока решений — те же числа и в том же порядке
  (период, шаг), чтобы «личности» пешек не менялись от яруса;
- **спасение за краем** — та же `escape`-проверка, на срезе: инвариант телеметрии свят;
- **promote посреди бегства**: вставить `UrgentPath`, подать настоящую заявку бегства,
  rescue-проверка (позиция могла уехать на непроходимый тайл — прямая не знает
  проходимости под ногами); **demote посреди бегства**: снять `UrgentPath`, заявку
  отменить (`to_idle` + направление).

Выпадение дальних из поштучных проходов: `interpolate_movable_transforms` — фильтр
`Without<FarTag>` (скрытым спрайтам трансформ не нужен; на promote — один раз записать
`Transform` из `SimPosition`); `pick_wander_targets` (Update) — `Without<FarTag>`;
`panic`-сбор (демоны × соседи) — `Without<FarTag>` в запросе гуляющих: в очаге орды
сбор паники ограничен ближним набором, дальние замечают демонов на своём срезе.
Спрайты дальних: `Visibility::Hidden` (запись значения на месте; extract/queue/sort их
не видят — проверено по 0.20.1), рисует их Ф5. Сепарация дальних не касается (она и так
только экран и зум < 0.75 — ближний набор).

**Детерминизм/реплей**: все дальние системы — `SimPipeline::Live`; под тумблером
детерминизма `FarTag` не существует вовсе. Пин: в детерминированном дворе после N тиков
ни одной сущности с `FarTag` (по образцу
`human_behavior_does_not_run_outside_the_world`). №44б не трогаем: новых источников
порядка ярус не вводит (срез фиксирован `PawnId`, решения — из тех же потоков).

**Риски**: штормы переходов на краях кадра при пане (гистерезис + выдержка; замерить
частоту переносов архетипов живьём при пане на орде); дальние бегущие толпой у стены
(прямая останавливается — пеший перебрасывается на срезе; визуально далеко не видно);
цена `check_visibility` O(n) по живым остаётся (200k — замерить; лечится Ф5 лишь
частично, остальное — принять).

**Замеры**: `sim/*_ms` по сегментам на 200k до/после (наивная точка — из Ф1);
`affordable` на виде внутрь города и на 0.4 (Париж владельца); частота переходов
(счётчик-зонд TEMP на звене, снять до коммита); `answers %failed` (дальние заявок не
подают — очередь должна опустеть).

**Готовность**: на 200k при зуме внутрь города `tick_ms` укладывается в бюджет 15×;
реплей-пины зелёные.

## Фаза 3 — Трупы: свежие спрайтами → запечённые чанками

**Файлы**: `silhouette/bake.rs` (новый), `human/corpse.rs` (очередь к запеканию),
`human/mod.rs`, `map/z.rs` (ничего не менять — см. ниже), `telemetry.rs` (счётчик
baked), `census.rs`, шейдер `assets/shaders/` по образцу `surface.wesl`,
`CLAUDE.md` (таблица сайтов спавна — строка трупных чанков).

**Механизм** (форма предложена владельцем; проверена по коду — детали ниже). Свежий
труп живёт как сегодня: тело + два кровяных ребёнка, кровь растёт
(`spread_blood`/`BloodSpread`, осадка `SPREAD_SECS` 1.6 с сим-времени). Когда лужа
доросла, `spread_blood` в той же команде, что снимает `BloodSpread`, ставит труп в
очередь «к запеканию» (`BakeQueue`-ресурс) — ноль сканирующих проходов, триггер уже
существует. Пекарь (система `Update`, гейт «рендерер есть» — `Silhouettes` собран)
пачкой за кадр (бюджет ~256 трупов; прецедент порций — `CrownStream::spawn_next` у крон):

1. читает окончательный вид тройки (глиф → UV-прямоугольник атласа, цвет, выросший
   `custom_size`, позиция/поворот/зеркало) и дописывает три квада в `CorpseField` —
   хранилище квадов чанка трупов (фиксированная сетка чанков ~500 м, не семантические
   районы);
2. помечает чанк грязным — перестройка меша чанка из хранилища по бюджету перестроек
   на кадр (грязных чанков за кадр — единицы);
3. ставит три сущности в очередь «к сдаче»; **деспавн — только в `FixedUpdate`**
   (правило CLAUDE.md «массовый деспавн не из середины `Update`»; слот — хвост
   `HumanBehavior` рядом с `rise_souls`, который уже снимает отжившие души), очередями по
   `commands.entity(..).despawn()`.

**Материал и z — проверка утверждений брифа**:

- Атлас — **не SDF**, а растр RGBA8 с мипами и линейной фильтрацией; запекание —
  обычные текстурированные квады, SDF не нужен. `ColorMaterial` в 0.20 умножает цвет
  вершин (`@if(VERTEX_COLORS)` в `color_material.wesl`) — путь «атлас-текстура + цвет
  вершины» бесплатен, прецедент — плоские слои карты (`map/surface.rs::Flat`,
  `meshing.rs` пишет `ATTRIBUTE_COLOR`). Единственное, чего `ColorMaterial` не умеет —
  **пол размера** (`min_px`): запечённый квад фиксированного мирового размера на
  городском зуме стал бы субпиксельным, а сегодня растягивается полом. Поэтому материал
  свой, «точечный» (см. словарь): квад разворачивается в вершинном шейдере из атрибутов
  «центр + полуразмер + пол» и клампится по uniform метров-на-пиксель — та же формула,
  что `Silhouette::drawn_size`. Если пол решат не спасать (открытый вопрос №3) —
  материал вырождается в `ColorMaterial` с атласом.
- **Z-полка не меняется вовсе**: свежий труп и сегодня лежит на плоском `Z_CORPSE`
  3.0 (`lay_down` пишет константу, не `unit_z`) — над дорогами (2.0) и пятном портала
  (2.8), под всеми живыми юнитами (`unit_z(y) ≥ Z_UNIT_BASE − 5700·0.002`, много выше).
  Чанк ставится на тот же `Z_CORPSE`; порядок внутри одного меша — порядок вершин
  (лужа → брызги → тело), тот же, что сегодняшняя z-иерархия тройки. «Потеря
  y-сортировки внутри чанка» относительно сегодняшнего вида — отсутствует: между трупами
  её и сейчас нет.

**Учёт и инварианты**. Запечённые исчезают из запроса `With<CorpseTag>` — инкрементальный
счётчик `Telemetry.baked` рядом с `killed` (BRP-читаемый, сбрасывается тем же
`WorldStarted`); `Census.corpses` показывает свежих, сумма — по надобности в HUD.
Инвариант `alive + killed + escaped == PopulationSize` не задет (трупы в него не входят,
`killed` инкрементален). Пины переписи — обновить под `baked` (тест-двор без рендера
пекарь не поднимает — там трупы остаются сущностями, пины двора не трогаем).

**Детерминизм**: рендер-сторона без RNG; деспавн трупа не трогает состояние симуляции
(компоненты трупа никто в тике не читает). В игре под тумблером детерминизма прогоны
остаются повторяемыми; реплей-двор (без рендера) не запекает вовсе — штатно.

**Выигрыш посчитанный**: (а) рост сущностей останавливается — вместо ~600k сущностей
к концу игры (тело + 2 ребёнка × 200k, ≈ гигабайт таблиц и компонентов — оценка,
«мерить при реализации») остаётся ~30 МБ хранилища квадов + ~90–100 МБ вершинных данных
GPU-буферов (3 квада × 4 вершины × ~40 Б × 200k); (б) запечённые покидают
`resize_silhouettes_on_zoom` (сегодня — O(n) чтений всех силуэтов на кадр движения
камеры, на эндшпиле — сотни тысяч), `FreshSilhouettes`, O(n)-проход видимости и
спрайтовый конвейер с квантованным кешем материалов крови (640 ключей на слой —
ограничитель исчезает вместе с носителем). Итоговые числа кадра — замером живьём.

**Риски**: всплеск запекания после большой волны (бюджет пачки сглаживает; очередь
не горит — труп никуда не спешит); растущее время перестройки одного чанка на
эндшпиле (хранилище квадов переписывается целиком — на 5–10k квадов это сотни
микросекунд, замерить; при нужде чанк режется надвое по сетке); первая редакция
печёт без пола размера, если владелец выберет простой путь (вопрос №3).

**Замеры**: кадр на эндшпиле (12k+ трупов — база soak №40: ~1 мс/кадр на спрайтах
крови) до/после; `entities` на 30-минутном прогоне с волнами (должен выйти на полку
«живые + свежие»); RSS/footprint против soak-плато 7.0G; кадр пана камеры на
эндшпиле (resize-проход без трупов).

**Готовность**: 30 мин 200k+волны — `entities` на полке, эндшпиль-кадр не дороже
сегодняшнего 12k-трупного; свежий труп неотличим на глаз от запечённого на том же
зуме; реплей-пины зелёные, пины двора не тронуты.

## Фаза 4 — Орды: фон + волны

**Файлы**: `demon/horde.rs` (новый: расписание и спавн волн), `demon/components.rs`
(`HordeStyle`, `WarpOrigin`; кап — дефолт 3500, потолок слайдера до 5000),
`demon/systems.rs` (происхождение в `spawn_demon`),
`demon/mod.rs`, `ui/` (вкладка Sim, секция Demon — новые ряда), `census.rs`
(строка орды), `rng.rs` (док-строка о ключах волн).

**Механизм**. `HordeStyle { wave_size, wave_every, wave_len }` — `SettingsGroup` с
persist, диапазоны `_MIN/_MAX/_STEP` рядом с ресурсом (конвенция), нулевой `wave_size`
выключает волны вовсе (фон-only — сегодняшний мир). `DemonStyle::cap` — **общий
потолок живых демонов** из всех источников (решение владельца №6): фон заполняет
до капа с повышенной скоростью (доработка владельца 2026-11-21 — «Открытые
вопросы» №2), волна выпускает `min(wave_size, свободное место)` — частичная
волна легальна и детерминирована; при полном капе волны вырождаются в пустые
затишья (трейд принят и подтверждён владельцем при ревью плана). Суммарное число живых демонов показывает Census.
Расписание —
ресурс `HordeSchedule { next_wave_tick, wave_index }`, тикает в `TickStage::Spawner`
тем же швом (до `DemonGrid` — синк-точка команд; залп и волна — один класс порядка):
когда `SimTick` доходит до `next_wave_tick`, волна `wave_index` разыгрывается из
**чистого потока** `stream(world_seed, RngDomain::Demon, HORDE_WAVE_KEY + wave_index)`
(создан и сброшен внутри одного вызова — как placement-поток; ключи волн — верхняя
половина пространства ключей, чтобы не пересечься с `pawn_id` демонов): очаг =
случайный проходимый тайл, интервал затишья, разброс позиций выпуска. Выпуск волны —
те же `spawn_demon` порциями по `wave_len` (всплеск команд размазан), `PawnId` из
общего счётчика `DemonSpawner` (уникальность — на ней стоят потоки и ключи диспетчера;
пин `every_spawned_demon_advances_the_counter_exactly_once` расширяется на смешанный
источник). Демон рождается с `WarpOrigin(очаг)`; политика блуждания «от происхождения»
вместо «от портала» — для порталальных демонов `origin == PortalPos`, вектор `away` тот
же бит-в-бит, число бросков не меняется (пин-тест эквивалентности). Внутри волны —
ничего нового: `acquire_targets` по людской сетке, заявки `MAX_CHASERS_PER_TARGET = 2`,
гистерезис ×1.5 — весь действующий chase.

**Панель**: секция Demon вкладки Sim — ряда `Wave size`, `Wave every` (затишье),
опционально `Wave length`; knob-kit как у соседей.

**Детерминизм/реплей**: расписание — функция `(seed, SimTick)`; каждый параметр волны —
из свежего потока по её номеру. Новых «живых» RNG-ресурсов нет. Пины: то же зерно — то
же расписание (юнит-тест чистой функции расписания); `a_restart_replays_the_run` с
включёнными волнами (реплей-двор, 64 пешки — волны там тривиальны); №44б-оговорка:
живой кросс-процессный повтор по-прежнему не заявляем, волны порядка не добавляют
(решения — из потоков по скиллу determinism).

**Риски**: стоимость acquire на 3500 демонов в плотном очаге — главный измерительный
риск фазы (миграция в Ф6); «волна вырезает район» — телеметрия kills/сек как здравый
смысл.

**Замеры**: `sim/acquire_ms`, `sim/chase_ms`, `sim/spawner_ms`, `demon_grid` на волне
3500; Census.demons; kills/сек; `affordable` на живом прогоне 20k+волны и 200k+волны.

**Готовность**: волны приходят по расписанию от seed, фон и волны живут под общим
капом, реплей-пины зелёные, слайдеры сохраняются между запусками.

## Фаза 5 — Дальней слой живых людей

**Файлы**: `silhouette/far.rs` (новый), `silhouette/mod.rs` (интеграция с resize и
`FreshSilhouettes`), `map/z.rs` (z слоя), `CLAUDE.md` (таблица сайтов спавна —
строка дальнего слоя).

**Механизм**. Точки дальних живых людей — тот же «точечный материал» и та же чанковая
сетка, что у трупов Ф3 (общий шейдер; демоны остаются спрайтами при всех зумах — их
3 500, ореол с блумом сохраняются, вопрос ореолов закрыт сам собой). Членство —
`FarTag` из Ф2; позиция точки пишется в буфер чанка на срезном тике пешки: скачок
0.35 м на 125 мс — на зумах слоя ≤0.1 пикселя, глазу не виден. Чанк помечается грязным
и переписывается раз в несколько кадров (срезы размазаны по `PawnId`, грязных чанков
за кадр — единицы). Смена зума — перестройка размеров точек (пол `zoom·HUMAN_MIN_PX`),
окном-бюджетом по образцу resize-кольца. Смерть/спасение убирает точку (события уже
есть: kill-обсёрвер, `escape`); рождение в далеке — спавн ставит точку. Resize-проход
силуэтов и `FreshSilhouettes` не трогают скрытых: фильтр `Without<FarTag>`, иначе окно
512 съедается дальними.

**Детерминизм/реплей**: слой — косметика `Update`/`Live`; реплей-двор без рендера его
не поднимает (как `Silhouettes::None` — не ошибка). В `SimPipeline::Live`.

**Риски**: стоимость перестроек на смене зума (замерить; бюджетное окно); O(n)
`check_visibility` по 200k живых остаётся — замерить; при необходимости — запись в
журнал производительности и отдельное решение (вариант: раздевание спрайта дальнего
до голой сущности — перенос архетипа на demote, уже редкий).

**Замеры**: fps/кадр на городском зуме 200k+волны до/после (точка «до» — из Ф1/Ф2);
кадр пересечения зум-порога; полный вид (Париж@0.4) против точки «до».

**Готовность**: полный отдалённый вид 200k идёт кадром ≥30 fps (машина владельца);
скрытие/показ дальних без стука; реплей-пины зелёные.

## Фаза 6 — Экономика демонов на 3500 (по данным Ф4)

**Файлы**: `spatial.rs`, `demon/behavior.rs`, `demon/mod.rs`.

**Механизм** (выбирается замером Ф4, кандидаты по убыванию простоты):
- `rebuild_demon_grid` → инкрементальная сетка (как людская; демоны не умирают —
  вставка на спавне, переезд через `moved`); rebuild O(3500)/тик ≈ 0.14 мс по пропорции
  с 0.004 на 100 — на грани бюджета, инкрементальность снимает;
- acquisition срезами: `acquire_targets` на `PawnId % 4` (задержка агро ≤47 мс —
  невидима), если `sim/acquire_ms` в очаге превышает бюджет;
- `chase` остаётся поштучным (лунж и кил обязаны быть тик-точными), но его точная цена
  на 3500 — входное условие фазы.

**Пины**: эквивалентность сетки rebuild/инкрементально (тест содержимого);
детерминизм срезов — тот же паттерн, что у Ф2. **Замеры**: сегменты тика на волне,
итоговый `tick_ms`. **Готовность**: демоны 3500 ≤ ~0.3 мс/тик; суммарный тик в бюджете
15× на 200k+3500, с запасом к 30× по CPU.

## Порядок и зависимости

```
Ф1 спавн ─► Ф2 LOD людей ─► Ф3 трупы: запекание ─► Ф4 орды ─► Ф5 дальний слой ─► Ф6 демоны ─► Ф7 приёмка
             (сим-бюджет)    (рендер/память)      (геймплей)  (рендер-бюджет)    (по замерам Ф4)
```

- Ф1 прежде всех: без 200k на сцене остальные фазы нечем мерить.
- Ф2 до Ф4: дешёвые люди — предпосылка честной цены орды (наивный 200k утопит волну
  в шуме).
- Ф3 после Ф2 (по решению владельца), от орд не зависит — с Ф4 меняться местами;
  материал и чанковая сетка Ф3 переиспользуются Ф5, поэтому Ф3 строго до Ф5.
- Ф5 закрывает рендер-лимитер городского зума; Ф6 — строго по данным Ф4 (возможно,
  кандидаты не понадобятся — тогда фаза сворачивается в замер). Ф7 закрывает цепочку.
