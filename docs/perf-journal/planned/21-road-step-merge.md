# Запланировано 21 — слияние проходов двух ступеней обочин: общая середина один раз, обочинные куски — на каждую

Приоритет: **1** — стена whole set = roads step 0 3.4–3.6 живьём
(записи 28–31); зданиевый лейн после записи 31 вышел из стены (2.5 против
3.4–3.6). Слияние проходов двух ступеней — «одна лента кладёт асфальт один
раз, тротуары/обочины — дважды» (запись 28) — последний крупный рычаг
дорожного лейна. Заморозка `map/prepare.rs` и `map/roads/*` для этого
заезда снята (правки записи 28 в master). Заезд 22.

## Проблема

После скелета записи 28 (`road_skeleton` один, `build_roads_from` на
ступень) оба финала всё равно молотят общую середину параллельно:
подготовка устьев/островков/разделительных, ленты, краска — у ступеней
бит-в-бит одинаковые (отпечаток записи 28: расходятся только
`road_verges`/`road_verge_lawns`/`road_verge_yards`/`sidewalks`
(−38 тыс. из 2.06 млн)/`lawn_scraps`). Дубль общей середины в финале s1 —
это CPU (~1.1–1.3 с бенча с параллельными нутрями) и дележ ядер под
стеной: живой лейн s0 3.4–3.6 против бенча ~2.3.

Ступень входит в сборку по сути одним булевым —
`VergeZoomBucket::draws_wide_verges()` (`verges.rs`): рисуются ли широкие
обочины. Через него ступенезависимы `kerb_returns` (скругления обочин),
`street_verge_geometry`, лоскуты и — через кербы — полосы тротуаров у
торцов; устья читают `kerb_returns`, так что ступенезависима и цепочка
устьев→клинья. Всё остальное финала — общее.

## Направление решения

1. **База**: бенч `map_meshing paris` ×3 на сторону, живая пара 3+3
   (порты 15704/15706, кеш с mtime, сосед на паузе) — метод записей 20–31.
2. **Разрез** (временные `eprintln` с меткой `perf22`, снятые до коммита):
   пофазно ОБА финала пост-скелета — сколько в каждом общего и сколько
   ступенезависимого; внутри ленточного прохода — вычисление против
   раскладки (толкают ли общие куски в оба набора сборщиков дорого —
   триангуляция в push-е); внутри scraps — куда делась разница 600/100.
3. **Форма слияния** — основная: один проход лейна строит **два полных
   набора сборщиков** (по набору на ступень): общий кусок считается один
   раз и толкается в оба набора (порядок толкания в каждом — прежний,
   геометрия бит-в-бит по построению); ступенезависимый — считается и
   толкается свой. `RoadBuild` остаётся на ступень, `prepare.rs` запускает
   **один** дорожный поток вместо двух, спавн-сторона (`spawn_map`,
   `spawn_road_meshes`, `show_road_steps`, `rebuild_roads`) не тронута —
   вершины/счётчики `road meshing:` обязаны сойтись бит-в-бит.
   - Если разрез покажет, что толчок в два набора дорог (триангуляция
     доминирует над вычислением), — общий кусок толкается один раз, хвост
     общих треугольников улицы копится в сборщик s0 и досыпается s1
     копированием треугольников (новый узкий API у `MeshBuilder`).
   - Параллельные секции общие: обочины обеих ступеней — один
     `in_parallel` по улицам (улица считает геометрию обеих ступеней),
     находка лоскутов обеих ступеней — один проход.
4. **Ожидание по стене** — честно: собственная работа лейна s0 не режется
   (скелет + общая середина + свои куски были и есть критический путь);
   рычаг — освобождение ядер из-под финала s1 (его параллельные нутри
   перестают молотить во время окна дорог) плюс минус ~1 с CPU лейна
   целиком. Запись 27 показала: срезание серийной работы финала двигало
   живой лейн на −0.3–0.5; здесь плюс освобождение ядер из-под второго
   финала. Суждение — только по живой паре 3+3; бенч может остаться
   плоским или чуть подрасти (кусочки s1 едут на критическом пути).
5. **Фолбэк** (если разрез покажет, что слияние — не один заезд: общая
   середина размазана по укладке, порядок фаз не поднимается одним
   движением): взять самый жирный ступенезависимый пункт по разрезу как
   узкий фикс + пунктир записи 30 (переиспользование базы inspect-индекса
   на смене стиля при игре, полный rebuild ~0.29 с, шов `apply_pieces`
   уже позволяет — брать, только если правка узкая и не задевает
   запрещённые файлы записи 30) или roof shadows 326 (wall 262 уже
   параллелен — скорее всего мимо).

2. **Worktree-пара** (прецедент записей 26–31): `.worktrees/perf22` —
   правка, базовая сторона — второй worktree на master; кеш `assets/osm/`

   `tools/seed-worktree-target.sh`.

   (`BRP_PORT=15704`/`15706`, `QWE_PERF_NOAPPNAP=1 QWE_PERF_NOVSYNC=1

   процесс каждой стороны — холодный, в медианы не брать; сосед на
   `brp pause` во время перезагрузок измеряемой стороны), лейны — строки
   `map meshes:`, тёплый старт — снапшот-хит → `warmup:`.
4. **Разрез** (п. 2), снят до коммита.
5. **Фикс** по решению п. 3 — мелкими коммитами, каждый с замером бенча.
6. Верификация (ниже), запись 32, строки в артефакт, коммиты, заезд 23.

## Верификация

- **Бенч** `map_meshing paris` до/после в одном состоянии машины: строки
  `roads` — целевые; buildings/fences — контроль состояния машины.
- **Живая пара** (worktree-пара одного состояния машины, 3+3 вперемежку):
  лейн `roads (verge step 0)` (стена), whole set, тёплый старт.
- Отчёт `road meshing:` бит-в-бит во всех прогонах обеих сторон (обе
  строки вершин + вся строка отчёта); `osm map:` / `polymesh stitched` —
  тоже. Геометрия по точкам — `brp probe` трёх точек бит-в-бит между
  сторонами; оффскрин-кадр плотного центра — только грубый фильтр (пешки
  дрейфуют, RMSE ~0.7 % без геометрии — запись 31).
- `tools/check.sh <файлы>` — зелёные: дорожные тесты (швы бит-в-бит,
  парити, порядок укладки), ярды реплеев, `a_restart_replays_the_run`,
  clippy, fmt.
