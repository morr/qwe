## Найдено (БЕЗ КОММИТОВ — правки кода угол не потребовал, TEMP-врезка снята до коммита)

- **Разрез без врезки**: лейны целого окна посчитаны по таймстемпам строк
  лога (owner view, Париж@0.4, Astar, тёплый снапшот) × CPU-время процесса
  (`ps -o time=` каждые 0.5 с, сэмплер с фиксированным pid). Окно whole set
  2.5–2.6 с, CPU в окне 23.4–23.7 CPU-s → утилизация 9.0–9.4 ядра из 10 —
  машина в окне упакована под потолок, свободных ядер нет. Лейны live:
  roads 2.5–2.6, buildings 1.8–2.2, polymesh 1.3–1.6, small 0.9–1.4,
  fences 0.67–0.82, navmesh 0.53–0.68, inspect 0.23 — Roads-стена
  (bench 1.1 → live 2.05 «road meshing») — честная доля CPU, не потери:
  переприоритизировать нечего, целое окно = ΣCPU/пропускную способность.
- **Решающий эксперимент**: TEMP-глобальный кап воркеров `in_parallel`
  (семафор на `workers()` разрешений, thread-local наследование для
  вложенных вызовов, env `QWE_PERF_WORKER_CAP=1`; parallel.rs, снят до
  коммита). Кап работает: maxThr 59–70 → 44–49. Живой A/B (base/cap/base,
  по 2 загрузки на сторону, чистые канарейки снапшот-рида 90.9–94.3 мс):
  base 2.90/2.80, cap 2.90/2.70, base 2.60/2.50 — окно плоское в пределах
  дрейфа серии. Переподписка (до 73 потоков) потерь не даёт. Вывод:
  лимит параллелизма и фронтирование окно не двигают — закрыто.
- **Бенч-разрез ΣCPU для следующего звена** (map_meshing, Париж, 2 прогона
  этой сессии — абсолюты ×1.5–1.6 баз №35, межсессионный дрейф машины,
  caffeinate не помогает; структура стабильна): три крупнейших лейна
  сопоставимы — road 1.52–1.96 (внутри: «437 мс до лент» — серийная голова,
  стейдж-разрез на темы ещё не делался), buildings shadows 1.57–1.62
  (facades+roofs 0.81, shadows 0.47–0.50, roof shadows 0.19),
  fences 1.75–2.16; parked cars 0.33, surfaces 0.16–0.21, rails 0.12.
  ΣCPU ~23.5: на roads+buildings+fences ~17; известные остатки всех трёх
  в сумме <1 CPU-s — следующая секундная экономия окна = новый стейдж-разрез
  внутри одного из трёх.
