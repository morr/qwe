Статус: разрез-заезд 44 (`planned/42-gpu-cut.md`). Фикса нет — плато
в лучшем смысле: GPU-стенки не нашлось, инструмент остаётся. Коммиты
`gpu_cut.rs` + `dev.rs` + `main.rs` + `Cargo.toml` (wgpu-типы) в
perf44 @ `b1ff23ee`. Worktree-пара `perf44-base` / `perf44` @ `d350f5e4`
(мастер-tip со спекой), кеш `assets/osm` с mtime (снапшот-хит, парсов
0), target посеян. Темп-патч 43 (`/tmp/perf44-temp.patch`) стоял сверху,
не коммитился.

**Инструмент** (`src/gpu_cut.rs`, гейт `QWE_PERF_GPU_CUT=1`, спайки
`QWE_PERF_GPU_SPIKES=<ms>`): маркер-системы в расписании `Core2d` на
шести границах кадра (0 до opaque, 1 opaque/transparent, 2 transparent/
post, 3 post/ui, 4 ui/upscale, 5 после upscale) открывают render pass
на 1×1-текстуру с одним фиктивным draw (три вершины, LoadOp::Load,
StoreOp::Discard) и `timestamp_writes` на начале пасса; энкодеры систем
уходят в сабмит в топологическом порядке (`RenderContextState:
SystemBuffer`), GPU исполняет их по порядку — начало пустого маркера =
кумулятивная GPU-граница, дельта соседних границ = длительность
сегмента. resolve в ring из четырёх MAP_READ-буферов, `map_async`
строго после сабмита, poll раз в кадр (`RenderGraph` после Submit),
main-мирный принтер: `gpu cut:` раз в секунду (средние сегментов +
зум камеры), `gpu spike:` пофреймово выше порога.

**Почему так** (всё проверено калибровочными прогонами): Metal не даёт
`TIMESTAMP_QUERY_INSIDE_PASSES` (RequestDeviceError — встроенная
диагностика 0.20 на Metal CPU-only, её «пустота» в записях 23/35 была
этим ограничением); `write_timestamp` на CommandEncoder bevy глушит на
macOS сам (фликер Tahoe, bevy#22257); энкодер без работы Metal молча
пишет нули («blit encoders won't write timestamps if they don't have a
blit operation», комментарий в wgpu-hal metal; воркараунд Dawn —
фиктивная работа), пустой compute pass дал все нули, render pass без
аттачментов wgpu 30 не валиден («at least one attachment»), а пасс с
draw-ом пишет. `Queue::get_timestamp_period` — наносекунды на тик
(Metal отдаёт сразу ns), не мс. map_async до сабмита — «buffer is
still mapped» на submit; ринг из двух ловил бы коллизию на тяжёлом
кадре, из четырёх — не ловит.

**Валидация** (живой прогон, Париж, порт 15704, сим на паузе для
зум-окон): `hide road` → transparent −0.04 мс; кроссинг зума вверх →
кронные чанки (263 шт) флипнулись hidden→visible и transparent
+0.04 мс; `Antialias` off → total в шуме окна; GPU-пики распределяются
по разным сегментам (bloom-пик в post 12.56, upscale-пик 8.54, opaque
пик 11.66) — маркеры стоят там, где задумано. `frame_time` 16.4–16.6 мс
(слот, 60 fps) при total ~0.5 мс — vsync-пробой согласован.

**Разрез** (медианы секундных окон, MSAA 4x, HDR, bloom, окно
1920×1080 логических = 3840×2160 физических):

|---|---|---|---|---|---|---|---|
| 4.50 | 2, кроны скрыты | 0.42 | 0.16 | 0.06 | 0.09 | 0.06 | 0.05 |

GPU занят ~3% слота vsync на самом тяжёлом зуме. Полоса пропускания
M1 Max (~400 ГБ/с) при плоских 2D-заливках съедает кадр города за
полмиллисекунды — гипотеза записи 5 («GPU-заливка 4K, MSAA+HDR+bloom
узкое место дальнего зума») снята: она была выводом из `frame_time`
без GPU-инструмента, а рендер-слот записи 52 — CPU-время.

**Кронная гипотеза заезда опровергнута.** «Слитые кроны ~956k вершин +
тени крон 5.5M на дальних зумах» — на дальних зумах их нет в кадре:
на ступени 2 (>3.5 м/px) видны только чанки плотных полос
(`TreeLodMask::of(0..=band)`, `TREE_LODS[2].density_cap = 2.0`), и все
263 парижских чанка получили band < 2 — скрыты; лес на 4.5 читается
заливкой `Wood`, как и написано в доке лестницы. Стоимость крон живёт
в диапазоне 0.2–3.5 м/px: ступень 1 добавляет +0.04 мс transparent
(0.06 → 0.10). Продуктовые рычаги записи 53 («меньше крон-сущностей
ближней ступени») GPU-числами не подкрепляются — кронная перебатчировка
флипа (54–63 мс) чисто CPU, GPU на кадрах кроссинга не пиковал (frame
spike 30–38 мс при нулевом `gpu spike`).

**GPU-шторм — только вход в мир**: `gpu spike` >8 мс — 925 за прогон,
из них ~95% в секундах входа (60/с в окне 13:33:09–26, доминанта
opaque 8–20 мс) — составная часть входного класса записи 53 (там
CPU-доминанта: trans-флеш + img2 апстрима). Вне входа — единичные:
bloom 7.5–12.6 мс, upscale 8.5, opaque 11.7 (первые кадры после
простоя, частоты GPU). Джерки дальнего зума (13:36:46–13:37:02, кадры
30–38 мс, без ввода) — CPU-чурн рендер-слота записи 53: `gpu spike` на
них нулевой.

**Вердикт — плато без GPU-стенки.** Рейтинг после заезда: рантайм при
планке 100 закрыт (52); джерки — плато (53, CPU-территория: кронный
флип — перебатчировка фазы, дальний зум — рендер-слот); GPU-сторона
кадра измерена и пуста — продуктовые рычаги записи 5 (render-scale,
MSAA-off ради GPU) не нужны, MSAA остаётся решением памяти, не времени.
Следующая тема — продуктовое решение по кронам-сущностям (53) либо
снижение планки.

**Метод** (новое к 51/52/53):

- **запуск — только `cd <worktree> && pwd && cargo run` одной
  командой**: рабочая папка шелла не живёт между вызовами — два запуска
  уехали в main checkout (сборка без инструмента, замеры мимо); `pwd`
  в первой строке вывода — обязательный контроль;
- `TIMESTAMP_QUERY_INSIDE_PASSES` на Metal не запрашивать:
  RequestDeviceError на создании устройства, из-за него же встроенная
  диагностика тут CPU-only;
- метки — только на границах пассов с работой в пассе; энкодерные
  записи на macOS bevy глушит (фликер #22257) — не обходить;
- `get_timestamp_period` — ns/тик; сначала сверить масштаб с известной
  стоимостью (bloom 4K ≈ единицы мс), потом верить сегментам;
- readback-цепочка: resolve → сабмит → map_async → poll → drain;
  map до сабмита = валидация «buffer still mapped» на submit;
- A/B-валидация инструмента до разреза: спрятать крупный слой,
  флипнуть ступень, выключить MSAA — инструмент обязан ответить в
  ожидаемых сегментах, иначе числа не про то.
