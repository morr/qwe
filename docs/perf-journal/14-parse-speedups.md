# Запись 14 — ускорение парса: Париж 6.42 → 5.2 с (−19 %)

Статус: фикс заезда 04 (`planned/04-parse-speedups.md`, пункт 4a и hotspots
профиля; 4b — бинарный снапшот — не взят) · замеры живого инстанса + офлайн
пробника (`pocket_probe`), до/после — stash-прогон в одном состоянии машины
под `caffeinate -d`.

**Было.** Тёплый старт Парижа ~19–24 с, из них парс 6.4–6.8 с — крупнейшая
последовательная часть до мешинга. План 4а предполагал, что карманы не
потокованы, — они уже потокованы (`in_parallel` и по дорогам, и по плиткам),
поэтому заезд начался с разбивки прохода по стадиям. Она показала: проход
плиток — 2.17 с (70 %), `corner_paving_contours` — 0.63 с, сцена — 0.84 с,
фартуки — 0.06 с; распределение по плиткам **плоское** (медленные плитки
200–400 мс при 1100–2600 контурах / 22–41k точках, ~10 мкс/точка), то есть
узкое место — суммарная работа объединения i_overlay, а не перекос планировки.
Состав входа объединения медленной плитки: обочинные кольца ~50 %, нарисованные
углы ~22 %, контуры площадей ~17 %, дорожные ленты ~13 %.

**Правки — три, по одному hotspot'у:**

1. **Входы** (`entrances/mod.rs`) — цикл по зданиям читает три неизменных
   индекса и своё зерно от первой вершины; дома друг от друга не зависят.
   Цикл переведён на `in_parallel` (результаты по порядку зданий, счётчики
   `walled_in`/`through` суммируются после по результатам). Париж 937 → 162 мс,
   Тула 45.5 → 13.4 мс.
2. **Карманы** (`parse/pockets.rs::road_covers`) — куски обводки одной дороги
   (лента по 16 звеньев + кольца обочин) объединяются в один `Cover` прямо в
   параллельном построителе: лента и её обочины налегают друг на друга по всей
   оси, и без этого каждое окно плитки разрешало те же пересечения заново.
   Одна обводка у дороги — без операции. Проход плиток 2.17 → 1.4–1.65 с,
   карманы целиком 2.93 → 2.54–2.68 с. Механика записана в
   `parse-geometry.md` (osm-map).
3. **Деревья** (`planting.rs::plant_standalone`) — нода сканировала все леса и
   все ряды (69 524 × 103 леса + 69 524 × 418 рядов); леса и ряды (с запасом
   `TREE_MIN_SPACING`) положены в bbox-сетку `Grid` (ячейка 100 м, как
   `GREEN_CELL` у покрытий дорожек) — кандидатов даёт одна ячейка. Одиночные
   232 → 177 мс, посадка целиком 0.70 → 0.66 с.

Контрольные точки правку не трогают и сходятся в пределах шума — дельта
парса **−1.2 с (−19 %)** относится к правке. Тёплый старт до играбельности
выигрывает меньше (~1 с): он доминирован мешингом (8.2–8.7 с стена) и штормом
warmup (4.3–4.4 с входа). Тула: входы 45.5 → 13.4 мс, карманы 268 → 270 мс,
деревья 239 → 243 мс — паритет за пределами входов; её парс и был мал.

**Счётчики.** Все совпали бит-в-бит (70 095 дверей, 24 763 одиночных дерева,
2 427 лесных, 3812/3812/1425/1425 в рядах), кроме посева карманов: Париж
18282 → **18275** (−7), Тула 6530 → **6529** (−1) — перестройка вершин
пересечений при перелепке обводок дороги, 0.04 %. Скриншот центра Парижа —
картина целая. check.sh (1513 тестов + детерминизм-ярды) зелёный.

**Отвергнутое — зафиксировано, чтобы не наступать:**

- **Дробление плиток** (адаптивные квадранты) не лечит проход: распределение
  плоское, цена объединения ~линейна по точкам — суммарная работа та же,
  стена не падает.
- **Обрезка кольца обочины до керба** (внутренняя цепочка дублирует покрытие
  ленты — `mapped_edge ≥ half`): сегменты не исчезают (две цепочки остаются),
  а цепочка, сдвинутая к краю ленты, — митер против фаски (`LineJoin::Bevel`)
  самой ленты — открывает на каждом изгибе щель-слюду между краем ленты и
  митер-точкой (без тротуара `reach = half`: дыра уже при лёгком повороте,
  у θ = 25° площадь 0.07 м² > `POCKET_AREA_MIN`) — ложные карманы на траве
  обочин. Трим не трогать.
- **Распараллеливание `kerb_returns`** (расклад `corner_paving_contours`:
  `Drawn::new` 310 мс + возвраты 348 мс из 600): поузловая часть — ~400 строк
  самого волосатого кода репозитория с записями в пер-дорожные массивы
  (`butt`/`setback`), приз ~300 мс. Отложено: соотношение риск/выигрыш не то.

**Что дальше.** Парс больше не крупнейшая часть тёплого старта — место занял
мешинг (стена 8.2–8.7 с: здания ~8 с лани) и шторм warmup Парижа (4.3–4.4 с —
заявки на входе, не таймаут). В плане остались: 4b — бинарный снапшот
`MapData` (парс 5.2 с → <1 с; инвалидация по `QUERY_VERSION` + `ParseKnobs`);
шторм демонов / очередь pathfinding на живом Париже (запись 11: без паузы
33.5 fps при tick 1.6 мс); волна archetype-передвижек (запись 3); цикл спавна
pathfinding-тасков и сорт кандидатов диспетчера (запись 9).

**Метод.**

- Офлайн-итерации — `cargo run --example pocket_probe -- x y paris`: весь парс
  без окна; временные `eprintln`-замеры стадий снимались до коммита.
- Строки `osm parse:` (карманы/входы/деревья с секундами) — первичный замер;
  они внутрипроцессные и повторяемы, стены прогонов шумят сильнее.
- Честное до/после — stash-прогон: `git stash push` → `cargo build` → прогон →
  `git stash pop` → пересборка. Контроль — фазы, которые правка не трогает
  (navmesh fill, гейты, мешинг).
- Прогон может открыться прошлым городом (prefs): город ставится
  `brp res set City . '"Paris"'`; свежая загрузка ждётся по счётчику строк
  `warmup:` в логе (старый маркер `brp ready` ловит предыдущую загрузку).
